## Problem Statement

Knight Code's skills and agents are only discoverable through hand-maintained prose, `SKILL-CATALOG.md` and `AGENTS.md`, kept in sync by convention rather than by any real check. Chris and every dispatched agent (Claude and subagents alike) currently pick a skill or agent by reading this prose rather than querying real structural data, the same way code lookups already go through `knightbrain_*` instead of memory or grep-first search.

## Demand Evidence

Confirmed, not hypothetical: an agent or subagent picking the wrong skill/agent has cost anywhere from a few wasted `Grep` calls to a whole decision made on the wrong lever, real tool calls and real tokens burned chasing the wrong search before landing on the right one. Separately, and mechanically more precise than first stated: a real session this week (checkpoint `b265cc0d`, 2026-08-02) found and deleted 32 confirmed duplicate skills from the global `~/.claude/skills/` install directory. The actual mechanism was a naming collision, not generic description overlap: an unprefixed skill (installed without the `knightcode-` prefix) sitting alongside a `knightcode-`-prefixed skill covering the same ground. The real risk was specifically routing risk, when Claude does natural-language description-matching rather than an explicit `skill:` name call, both the prefixed and unprefixed versions' descriptions are in play, and the unprefixed, non-Knight-Code-owned copy could get picked by mistake. That same session also caught and avoided a false positive, a skill initially suspected as a duplicate ("the learn skill") turned out to be genuinely unique on closer inspection, real evidence that naive similarity matching needs a guard against over-flagging, not just a threshold tuned to catch the real cases. All 65 `knightcode-`-prefixed skills were confirmed untouched; only the colliding unprefixed copies were removed. `TODOS.md`'s own count of "41 skills from 3 upstream batches" is itself stale against the live `git log` (a fourth batch, commit `d3c4ee5`, ported 9 more skills from `agentic-awesome-skills` and `mattpocock/skills`, un-reflected in that count), a small live demonstration of the exact hand-maintained-prose-drift problem this design exists to fix. Both the misrouting cost and the collision-duplication cost are real, already-paid, not projected.

**Revision 2 addendum, a second real incident this scope never considered:** a separate cost exists alongside misrouting and duplication, unauthorized resource access by dispatch. A session dispatched `subagent_type: "loremaster"` via the Agent tool, directly against loremaster's own Wake-Up Protocol ("this conversation IS loremaster for the session, no subagent, no relay") and against Chris's standing rule that only loremaster-in-conversation and loreGod may operate in the campaign vault. The only reason this surfaced at all was reading loremaster's full agent body after the fact, nothing checked it before the dispatch ran. The fix that landed, `hosts/claude/hooks/vault-agent-gate.ts`, is a hand-written PreToolUse hook matching on `subagent_type` and a hardcoded list of vault-name string markers in the prompt text. It works, but it has to be manually kept in sync with which agents own which resources, the same drift risk as `SKILL-CATALOG.md`/`AGENTS.md` themselves. Independent confirmation this is a real, not hypothetical, category of failure: current field research on AI agent permission scoping states plainly that a written policy, system prompt, or instruction may define what should happen, but it is not a control boundary if the AI system can still execute the prohibited action through available tools or credentials. `vault-agent-gate.ts` is exactly this weaker form, a prompt/hook-level guard, not a structural one. KBV2.md's original Part 2 scope, before this design's first approved pass narrowed it to duplicate detection, proposed exactly the fix for this: an `owns` edge type, so a dispatch can be checked against real graph data (does this subagent type have a declared ownership edge to this resource) instead of a regex over prompt text. This revision confirmed, via a direct fetch of `colbymchenry/codegraph` (a real, live coding-agent knowledge-graph tool), that no existing external tool covers either this or the duplicate-detection problem, both index source code only, neither tracks ownership or skill/agent relationships. Both problems are genuine gaps only Knight Code's own `lorebrain` extension closes.

## Status Quo

Right now, finding the right skill or agent means reading `SKILL-CATALOG.md` and `AGENTS.md` as prose, or falling back to `Grep`/`Glob` over `.claude/skills/` and `.claude/agents/`, neither of which is checked against what's actually registered (`list_agents`, the live Skill tool listing). Naming collisions (an unprefixed skill duplicating a `knightcode-`-prefixed one) are caught only by a human manually comparing the full installed skill list, the same way the 32 duplicates were found.

## Target User & Narrowest Wedge

Target user is Chris himself and every agent (primary or subagent) operating in this repo, since misrouting and wasted search apply to both equally. Narrowest wedge: run the existing `lorebrain` skills-mode indexer against Knight Code's own root (Part 1, zero code changes), and extend it to also index `.claude/agents/*.md` as first-class graph nodes with real edges (Part 2), plus one deterministic overlap-detection pass over the resulting skill nodes, so both stated pains (drift-driven misrouting and undetected duplication) are addressed in the first shippable build rather than only one of them.

## Constraints

- No new indexing engine, no vector store, no embeddings, this reuses `lorebrain`'s existing deterministic AST/markdown-extraction pipeline (`lorebrain/src/skills.ts`, `lorebrain/src/types.ts`, `lorebrain/src/freshness.ts`), the same one already powering `knightbrain`, `knightbrain-source-readonly`, and `lorebrain` itself.
- Schema changes land in `lorebrain/src/types.ts`, a file shared by all three MCP registrations, changes are additive but need to be walked through before editing since all three servers share the binary. Because `lorebrain` (the D&D campaign vault tool) shares this same file, a known-good `lorebrain_query`/`lorebrain_search` call against the campaign vault must be run before and after the schema change to confirm no regression there, not assumed safe from additivity alone.
- Redundancy/overlap detection must stay deterministic (token/set-overlap over frontmatter fields), not a similarity model, to stay inside the existing no-embeddings design constraint. Verified directly against `lorebrain/src/skills.ts` and real `SKILL.md`/agent files (correcting an earlier wrong assumption in this doc): the current extractor only parses frontmatter `name` and `description`, it does not parse any tool-declaration field at all today, and the two node types use genuinely different fields with different shapes. Skills declare `allowed-tools:` as a YAML list (e.g. `knightcode-cso/SKILL.md`: `allowed-tools:\n  - Bash\n  - Read\n  - Grep`); agents declare `tools:` as a flat comma-separated string, inconsistently spaced across real files today (`tools: Read, Write, Bash` vs `tools: Read,Glob,Grep`). Part 2 therefore includes two small, separate parsers, one for each shape, both feeding a common `Set<string>` on the node, not one shared `tools:` parse as originally (incorrectly) written here. A distinct "trigger phrase" field doesn't exist as structured extractor output either (most current `SKILL.md` files fold trigger phrases into free-form description prose), so it stays out of the overlap computation for the first build rather than becoming new extraction work smuggled into Part 2. A skill or agent file with no tool-declaration field present contributes an empty set to that one signal rather than being excluded from the graph entirely.
- `parseFrontmatter`'s existing continuation-line logic folds an indented YAML list into a single space-joined string (verified against how it would handle `allowed-tools:`'s block-list shape); this works but needs its own explicit unit tests (see Success Criteria) rather than being assumed correct because it already parses flat `description` fields fine today.
- An existing, separate silent-drop mechanism already exists in `discoverSkills` (`skills.ts`, `seen.has(name)`, "user skills win over repo copies"): if a skill's frontmatter `name` exactly matches one already seen during the user-dir-then-repo-dir scan, the second copy is dropped before it ever becomes a node, no edge, no warning. This is distinct from both Tier 1 (near-identical prefixed/unprefixed name variants) and Tier 2 (soft overlap). **Corrected during the build: the shadowing risk described here was real but the framing was inverted.** The repo's top-level `<name>/` directories are build sources the host never loads, and `~/.claude/skills/knightcode-<name>/` is the installed copy the host actually runs, so scanning both made one skill appear twice rather than exposing a stale shadow. The indexer now scans only real skill locations (the user skill directory, and `<repoRoot>/.claude/skills`), and install-versus-source divergence is caught by a dedicated drift check (`bun run skills:check`) rather than by the graph.
- Single-user, single-operator scale: dozens of skills and agents, not hundreds, so this explicitly does not need the dynamic vector-retrieval architecture the wider industry defaults to at 50+-tool scale (see Cross-Model Perspective).
- Only skills and agents that are actually registered files (`SKILL.md` under `~/.claude/skills/` or the repo, `.claude/agents/*.md`) become graph nodes. Agents `AGENTS.md` catalogs as queued-to-be-built (loreGod's peers, Shamu, the impeccable sub-agents) that have no real file yet stay absent from the graph, the same way they're absent from `list_agents` today, no placeholder nodes.
- Verified directly: 3 of 8 current agent files (`loremaster.md`, `devknight.md`, `obsidian.md`) declare no `tools:` frontmatter at all, meaning "all tools" per Claude Code's own convention, not "no tools." Their `invokes` edge set reflects that distinction explicitly (a tagged "unrestricted" node property), rather than silently rendering as an empty edge set indistinguishable from a genuinely tool-less agent.
- `SKILL-CATALOG.md` and `AGENTS.md` stay hand-maintained by the existing same-session-update convention for the duration of this build. They are not superseded until Part 4 (generated catalogs) actually ships.
- `query.ts` and `report.ts` currently filter nodes/edges through hardcoded literal type lists (e.g. `query.ts`'s definition filter: `n.type === 'function' || n.type === 'class' || n.type === 'skill' || n.type === 'tool'`), not an exhaustive switch. Adding `'agent'` to `NodeType` (and `'duplicates'`/`'overlaps'` to `EdgeType`) is TypeScript-safe and will NOT raise a compile error at any of these sites, meaning agent nodes and the new edges would silently fail to resolve through `knightbrain_def`/`_refs`/`_query` and silently never appear in `GRAPH_REPORT.md`'s summaries unless every such literal list is found and updated by hand as part of the same change, not as a separate follow-up that can slip. This is the same silent-exclusion failure shape already recorded twice in this project's own `learnings_search` history for this exact query engine. **Revision 2 addendum:** the same silent-exclusion risk applies identically to `'resource'` (NodeType) and `'owns'` (EdgeType), both added below, so the literal-list audit covers five new types total, not the three named here originally.
- `freshness.ts` explicitly bypasses staleness checking for `mode: 'skills'` today (`ensureFreshGraph` returns a plain load with no mtime comparison for that mode, unlike `code` mode's automatic reindex-on-change). Left as-is, this design's entire premise, replacing hand-maintained prose that drifts from what's registered, gets a new silent-drift hole one layer down: add a skill or edit a description, and the graph is stale with zero warning until someone remembers to manually re-run the indexer. Chris confirmed this gets fixed as part of this build, not deferred: extend `ensureFreshGraph` to cover `skills` mode using the same mtime-scan approach `code` mode already uses, scanned over `~/.claude/skills/*/SKILL.md`, `<repoRoot>/.claude/skills/*/SKILL.md`, and `.claude/agents/*.md` (corrected during the build from "the repo's own `SKILL.md` dirs", which would have scanned build sources rather than registered skills).
- **Revision 2 addendum:** a third new `EdgeType`, `owns`, joins `duplicates`/`overlaps` in this same schema pass, sourced from two genuinely different mechanisms, not one, resolved after the spec review flagged this as ambiguous in an earlier draft. **Skill-to-agent ownership** is a one-time migration, not ongoing parsing logic: a human (or a one-off migration script, run once and then discarded) applies the extraction rule below against `SKILL-CATALOG.md`'s current "Associated agent" column, and writes the result directly into a new SKILL.md frontmatter field on the handful of skills that genuinely have one. From that point on, `skills.ts` just reads that frontmatter field on every index run, exactly like it already reads `name`/`description`, no parsing risk at index time, because the risky part happened once, up front, and was verified against the fixture below before anything got written. **Agent-to-resource ownership** is the opposite: real, permanent extraction code, since `AGENTS.md`'s persona table is read live on every index run (a genuinely new input path and a new table-row parser, `skills.ts` does not read `AGENTS.md` at all today), and the AGENTS.md table stays the source of truth going forward rather than being migrated into frontmatter. Both paths land as `owns` edges in the graph.
- **Revision 2 addendum, ownership-extraction risk (corrected after spec review):** the extraction rule behind both paths is not risk-free direct extraction, it is pattern-matching over free descriptive prose and carries real false-positive/false-negative risk, the same class of risk Tier 2 already accounts for with a fixture and a tuned threshold. Verified directly against real content: `SKILL-CATALOG.md`'s "Associated agent" column mixes genuine owning-agent names with unrelated backtick-quoted mentions in the same cell (e.g. one row reads "None, `investigate` offers to run it...", where a naive first-backtick-token extraction would wrongly read `investigate` as the owning agent). The extraction rule must be explicit and narrow: only a backtick-quoted token that also matches a real, registered agent id (confirmed against `list_agents`, not just present in the graph) becomes an `owns` edge target; a cell reading "None" or naming something that isn't a registered agent produces no edge. For the skill-to-agent path, this rule runs once, during the migration, against a small fixture (a handful of real `SKILL-CATALOG.md` rows, including the known "None, `investigate` offers to run it" hazard case), the same discipline already applied to Tier 2, and the resulting frontmatter fields are what ships, not the rule itself. For the agent-to-resource path, since it runs live on every index going forward, the same fixture discipline applies but the rule itself is what ships as ongoing code, not a one-time output.
- **Revision 2 addendum, the AGENTS.md-side rule (corrected after spec review, this was left unspecified in an earlier draft):** verified directly against the current `AGENTS.md` custom-agents table, its "What it's for" column is free descriptive prose with no existing backtick-quoted resource reference for loremaster's vault ownership today, the actual ownership statement lives in `CLAUDE.md`'s "Operating a live Obsidian vault" section and in `vault-agent-gate.ts`'s own hardcoded marker list, not in a machine-parseable form in `AGENTS.md` itself yet. Rather than attempting to pattern-match a resource name out of prose that was never written to be parsed, this build includes a small prep step: add an explicit, backtick-quoted resource reference, `` `revenge-of-the-felled-god` ``, to loremaster's `AGENTS.md` row (any other agent with a real, exclusive resource claim found during this pass gets the same treatment, its own backtick-quoted token), then apply the identical extraction rule already defined for the skill side, a backtick-quoted token matched against a small, explicit registry of real resource ids (not a free-text pattern match), symmetric with Tier 3's `SKILL-CATALOG.md` rule rather than a separate, looser one. The token written into `AGENTS.md` is the same string the `resource:<slug>` id is built from (see the schema constraint immediately below), not a separately chosen name.
- **Revision 2 addendum:** `owns` edges need a real target node for non-file resources named in `AGENTS.md` (e.g. the campaign vault is not a skill, agent, or tool file and has no existing node to point at). This requires one more schema addition beyond `agent`: a `resource` `NodeType` for named, non-file targets. The id scheme is fixed as `resource:<slug>`, where `<slug>` is the exact backtick-quoted token added to `AGENTS.md` during the prep step below, not a separately-derived name, so there is exactly one canonical string, not two. Concretely: `resource:revenge-of-the-felled-god`, matching the project slug `lorebrain` already uses for this same vault's own graph storage directory (`~/.lorebrain/revenge-of-the-felled-god-<hash>/`), not an invented alias like "campaign-vault." Without this, the loremaster-to-vault success criterion below has no real edge target to resolve to.
- **Revision 2 addendum:** an `owns` edge whose declared target (a SKILL-CATALOG.md-named agent, or an AGENTS.md-named resource) doesn't resolve to a real node (typo, or a queued-but-unbuilt agent per the existing constraint above) produces no edge and no silent placeholder, consistent with how unbuilt agents are already excluded from the graph. Worth a warning surfaced during the build/verification step, not necessarily a permanent runtime check.
- **Revision 2 addendum:** wiring an actual dispatch-time enforcement check (replacing `vault-agent-gate.ts`'s hardcoded hook with a real query against `owns` edges) is explicitly out of scope for this build. This design only makes the ownership data real and queryable; using it to gate a live dispatch is a separate, later follow-on once these edges exist and are trusted.

## Premises

1. The real cost has two faces: wasted tool calls/context burned searching the wrong way before finding the right skill/agent, and outright wrong decisions made by pulling the wrong lever. Confirmed by Chris directly.
2. Once skill/agent frontmatter (name, description, tools) is complete and accurate, querying a structural graph for "which skill/agent handles X" is a legitimate deterministic lookup, not a guess. No new hook or nudge mechanism is required beyond CLAUDE.md's existing "structural lookup first" rule, once the data exists to query. This is why Part 1's acceptance step (below) has to actively confirm frontmatter completeness rather than assume it, the Problem Statement's whole complaint is that the hand-maintained catalogs already drift from what's registered.
3. Skill/agent redundancy and overlap detection is a core, in-scope part of this design, not an adjacent problem to defer, confirmed directly by the 32 duplicated skills already found and removed by hand this week, a naming collision between prefixed and unprefixed installs, not generic description drift.
4. SkillX's principles (three-tier planning/functional/atomic hierarchy, and a refinement loop that merges overlapping entries and filters bad ones) are worth adapting, not adopting wholesale, mapped loosely onto Knight Code's own agent/skill/tool layers.
5. Parts 1+2, including overlap detection, remain the real wedge for this week. Auto-freshness (Part 3) and generated catalogs (Part 4) stay follow-on value once Parts 1+2 are built and trusted.
6. **Revision 2 addendum:** ownership-edge data (ties back to the `vault-agent-gate.ts` incident) and duplicate/overlap-edge data (ties back to the 32-skill incident) are two independently real problems that happen to share the exact same shared schema file. Building both in one pass is a risk reduction, not scope creep, since it avoids a second future walkthrough, a second campaign-vault regression check, and a second `query.ts`/`report.ts` literal-list fix against the same three-server-shared file. Confirmed directly with Chris.

## Cross-Model Perspective

No live cross-model second opinion was run this session (skipped by Chris). Two pieces of external research fed the premises directly instead:

**Industry knowledge-graph-for-agents research**: the field's standard fix for tool-catalog drift is dynamic vector-similarity retrieval, justified by research showing selection accuracy degrading past roughly 50 tools in a catalog. That threshold doesn't apply here, Knight Code's real catalog is dozens of skills/agents, not 50+, and the actual observed failure was stale hand-written prose causing a wrong pick, not context exhaustion from too many options. A deterministic structural graph, the same engine already trusted for code, is the correct shape for this specific failure mode: inspectable edges an agent can `_def`/`_refs`/`_callers` through, not a similarity score to trust blind.

**SkillX (zjunlp/SkillX)**: a research paper on constructing a skill knowledge base for LLM agents learning from their own trajectories, organized into planning/functional/atomic tiers via an extraction/refinement/expansion loop. Different problem than KBV2 (trajectory learning vs. static frontmatter indexing), but its refinement phase, explicitly merging redundant skills and filtering low-quality ones before they're queryable, transfers directly: Knight Code has the same redundancy problem, just discovered by hand instead of by a repeatable mechanism.

**Revision 2 addendum, external research feeding the ownership-edge premise:** a search on agent permission-scoping and capability-graph research confirmed independently that instruction-only or policy-only prohibitions are considered low-enforceability by the field, real technical scoping is required alongside them. This directly validates treating `owns` edges as real, queryable graph data rather than another hardcoded hook. A direct fetch of `colbymchenry/codegraph`, a live, real 2026 pre-indexed knowledge-graph tool for coding agents (Claude Code, Codex, Cursor, and five others via MCP), confirmed it indexes source code only and carries no skill/agent/ownership concept at all, ruling it out as something that already solves either half of this design's Part 2 scope.

## Approaches Considered

### Approach A: Minimal viable, Parts 1+2 only
Run the existing skills indexer, add agent nodes/edges exactly as originally scoped in KBV2.md. Defers redundancy detection entirely.
Effort: S/M. Risk: Low. Reuses the `lorebrain` engine, storage, and MCP surface fully.
Pros: fewest files, smallest diff, ships fastest, zero new algorithmic surface.
Cons: violates premise 3, defers what Chris named as core; does nothing about the 32-duplicate problem, and, per Revision 2, does nothing about the separate vault-agent-gate ownership incident either, since both are now treated as equally core scope being merged into Approach B.

### Approach B: Parts 1+2 plus a three-tier duplicate/ownership edge set (RECOMMENDED, build first)
Same base build as A, plus a small extractor extension (`skills.ts` gains two separate parsers, `allowed-tools:`'s YAML list for skills and `tools:`'s comma string for agents, corrected after spec review from an earlier, incorrect "one shared `tools:` parse" framing, see Constraints) and a three-tier deterministic post-process, shaped around the actual observed failures rather than a generic similarity score:

- **Tier 1, name collision (the real incident's mechanism, hard signal)**: for every unprefixed skill node, check whether a `knightcode-<same-or-near-identical-name>` node exists. An exact or near-exact name match (stripped of the prefix, case/hyphen-normalized) emits a `duplicates` edge directly, no threshold tuning needed, this is the deterministic check that would have caught all 32 real duplicates on its own.
- **Tier 2, description/tool overlap (softer signal, secondary)**: for pairs that don't collide on name, compute token-overlap similarity over normalized description text and shared tool-declaration sets (drawn from the two separate parsers above, pure set/string comparison, no embeddings), emitting a softer `overlaps` edge above a threshold, for the case of two differently-named skills that still cover near-identical ground.
- **Revision 2 addendum, Tier 3, ownership (a third edge, corrected after spec review to carry its real risk level and mechanism)**: `owns` edges from two genuinely different sources. Skill-to-agent: a one-time migration, the narrow extraction rule below runs once against `SKILL-CATALOG.md`'s current content, verified against a fixture, and writes its output straight into a new SKILL.md frontmatter field, which `skills.ts` then reads live like any other frontmatter field, no ongoing parsing risk. Agent-to-resource: real, permanent extraction code, a new table-row parser reading `AGENTS.md`'s persona table live on every index run, plus a matching new `resource` NodeType for non-file targets like the campaign vault. An earlier draft of this addendum called this tier risk-free direct extraction and left the migration-vs-live distinction unstated; the spec review correctly caught both: recognizing an owning agent inside `SKILL-CATALOG.md`'s free-text "Associated agent" column (which mixes real agent names with unrelated backtick-quoted mentions) is pattern-matching with real false-positive risk, the same class Tier 2 already accounts for, and it matters whether that risk is retired once (the migration) or carried forever (the live AGENTS.md parser). Both paths get the same treatment: a narrow extraction rule (only a backtick-quoted token that also matches a real registered agent id) and their own small fixture built from real `SKILL-CATALOG.md`/`AGENTS.md` content, including the known hazard case, before being trusted.

All three edges queryable via the existing `knightbrain_query`/`_refs` surface with `mode: 'skills'`.
Effort: M/L (revised up from the original M; the `resource` NodeType, the new `AGENTS.md`/`SKILL-CATALOG.md` table parser, and Tier 3's own fixture are real added surface, not free). Risk: Low for Tier 1 (deterministic name match, no tuning), Medium for Tier 2 and Tier 3 alike (both need a tuned rule validated against a real fixture before being trusted). The 32 real duplicates are gone with no git trace (deleted uncommitted at the global install location, not the tracked repo), so they can't be restored as a real fixture, but Tier 1's logic can be validated directly against the current, real skill list (any remaining `knightcode-<name>` vs. unprefixed `<name>` pairs) without needing a fixture at all. Tier 2 needs a small hand-built fixture: a handful of synthetic near-duplicate pairs plus at least one deliberately near-miss pair modeled on the real "learn skill" false positive (similar-sounding name or description, but a genuinely different scope), checked into a scratch location, run through the overlap pass, requiring the synthetic duplicates to surface as `overlaps` while the near-miss pair and the real current skill set both stay clean. Start Tier 2's cutoff from a concrete Jaccard/token-overlap value (e.g. 0.6 over normalized description-token sets) and iterate from there against that fixture, rather than tuning blind. Tier 3 needs its own fixture (real `SKILL-CATALOG.md` rows, including the "None, `investigate` offers to run it" hazard case) and, separately, direct validation that the loremaster-to-vault edge specifically resolves against real `AGENTS.md` content, since that's the exact incident this closes.
Reuses the `lorebrain` engine, storage, and MCP surface fully; adds one small extractor change, a new table-row parser, a new `resource` NodeType, and three new deterministic computation steps, no new infra beyond that.
Pros: Tier 1 directly targets the actual duplicate incident with no tuning risk at all; Tier 2 and Tier 3 both catch their respective classes of overlap/ownership without embeddings; all three stated pains addressed in one build touching the shared schema exactly once.
Cons: three edge types plus a new node type is more surface area than a single generic score; both Tier 2 and Tier 3 need real tuning against fixtures rather than being free extraction; the combined diff is larger than shipping duplicate detection alone would have been, and larger than the first draft of this addendum estimated.

### Approach C: Full SkillX-tiered vision, long-term destination
Explicit three-tier node typing (agent = planning, skill = functional, tool/CLI-invocation pattern = atomic, as first-class nodes rather than implicit edge targets), the overlap edge from B, plus a periodic refinement agent that proposes merges/deprecations (never auto-applies, consistent with this project's no-silent-mutation norms) feeding directly into Part 4's generated catalogs.
Effort: XL. Risk: Medium-High, biggest schema change, most new surface area.
Pros: best long-term trajectory, matches SkillX's full refinement loop rather than just detection.
Cons: overkill as a first build; the tiering and refinement-agent pieces are not needed to ship real value this week.

## Recommended Approach

Build B first, ship it this week. Design the Part 2 schema so C's later additions (explicit tier typing, a periodic refinement agent) are additive extensions of B's graph, not a rewrite, since B's overlap edge is the same underlying computation C needs, just without the explicit tiering or the active refinement loop on top. A stays in the doc only as the honest minimal-viable comparison, it is not the recommendation because it defers a premise Chris named as core.

## Open Questions

- Tier 2 threshold tuning (see Approach B) is a prerequisite gate, not a parallel task: it must complete against the hand-built synthetic fixture, including the near-miss pair, before the `overlaps` edge is trusted for anything else, including being called a met Success Criterion below. Tier 1's name-collision check has no equivalent gate, it is deterministic and validated directly against the real current skill list, but does need its own explicit near-miss case named (two genuinely different skills that happen to share a normalized name stem, e.g. `review` vs. `knightcode-review-animations`) so it doesn't false-positive the way Tier 2's naive form could have.
- Should either edge, once computed, surface anywhere active (a warning at skill-creation time) or stay a queryable signal Chris checks periodically? Not decided this session.

### Working-directory drift broke every project hook mid-session, unrelated to the diff itself

While verifying the review and simplify passes via direct CLI (`cd lorebrain && bun run src/cli.ts ...`, per the freeze-avoidance process above), every one of Knight Code's five Bash-triggered hooks (`pretooluse-hygiene-gate.ts`, `nested-repo-gate.ts`, `bash-output-budget-hook.ts`, `vault-sync-nudge-hook.ts`, `post-commit-simplify-nudge-hook.ts`) started failing with "Module not found", visible to Chris in the Claude Code UI as a repeating block of PreToolUse/PostToolUse hook errors.

Root cause: each hook's `.claude/settings.json` command is a path relative to the repo root (`bun run hosts/claude/hooks/<name>.ts`). Running `cd "<...>/lorebrain" && bun run src/cli.ts ...` as a single Bash call repeatedly, rather than scoping the `cd` to a subshell, left the session's persisted working directory sitting in `lorebrain/` for every call after the first one. Claude Code's hook runner resolves each hook's relative path against that same persisted directory, so once it was `lorebrain/` instead of the repo root, none of the five hook paths could resolve, all five failed at once, and the failure had nothing to do with any of the code the hooks themselves run.

**Misdiagnosis worth recording plainly, not glossing over:** the first read on this, before checking, was that it must be the same root cause as the same-day WT/AppInfo terminal-freeze incident (a system-wide process-spawn lock), since "every hook failing at once with no shared code" looked identical to that shape of failure. Chris confirmed a full restart had already happened and the failures started exactly when KBV2 work began, before the WT freeze occurred, before ever checking the actual mechanism, based on that surface-level pattern match. Confirming it directly (checking `pwd`, then deliberately reproducing and un-reproducing the drift) took under a minute and immediately falsified the AppInfo theory; the guess added a full round of avoidable back-and-forth that a five-second `pwd` check would have skipped entirely.

**Fix, both parts:**
1. Session-level: never chain `cd <dir> && <command>` as a bare compound command when a hook-triggering Bash call might follow. Wrap it in a subshell instead, `(cd "<dir>" && <command>)`, confirmed directly to leave the persisted working directory untouched afterward, unlike the bare chained form.
2. A second, real, unrelated bug surfaced by the same investigation: `post-commit-simplify-nudge-hook.ts`'s `changedCodeFiles()` used `execSync('git show ...')`, which spawns `cmd.exe` on Windows to interpret the command string. That spawn had been failing outright (`ENOENT ... uv_spawn 'C:\WINDOWS\system32\cmd.exe'`) every time a `git commit` landed in the separate KnightOS project, logged 16 times in `~/.knightcode/hook-errors.log` going back to July 30, well before this session, always failing open (never blocking the commit) so it went unnoticed until directly asked about. Fixed by switching to `execFileSync('git', ['show', '--name-only', '--pretty=format:', 'HEAD'], ...)`, which runs `git.exe` directly with an argument array and needs no shell spawn at all. Verified directly against the real KnightOS repo: clean allow response, no new entry in the error log.

Both fixes are outside the KBV2 diff itself (`hosts/claude/hooks/post-commit-simplify-nudge-hook.ts`, plus this session's own subshell discipline going forward), noted here because they surfaced from KBV2's own verification process and Chris asked for the incident recorded so the same misdiagnosis and the same drift don't recur.

### Step 6, Tier 2 (soft overlap) built, gated against a fixture, and verified

**Fixture first, per the plan's own gate.** `lorebrain/test/fixtures/overlap-repo/.claude/skills/` holds six hand-built skills covering all three cases the design named:
- A true near-duplicate pair, `deploy-to-prod` and `release-it`: different names, identical description and identical `allowed-tools`. Must be flagged.

- A Tier 1 name-stem near-miss, `review` and `knightcode-review-animations`, the exact pair the design named as the risk case. Must not produce a `duplicates` edge.

**Scoring, deterministic, no embeddings.** `descriptionTokens` lowercases, strips punctuation, drops tokens of two characters or fewer, and removes a stopword list (the generic "use when the user asks to" scaffolding almost every description shares, which otherwise makes every skill look partly like every other). `overlapScore` is a weighted Jaccard: 0.8 times description-token overlap plus 0.2 times declared-tool overlap. Description carries the weight because tools are coarse, a large share of the catalog declares `Read`. An empty tool set on either side contributes zero rather than counting as a match, so two skills that both declare nothing are not treated as tool-identical (covered by its own test). A pair already reported by Tier 1 is skipped rather than also emitting a weaker `overlaps` edge over the same pair.

**Threshold set from measured data, not guessed.** `OVERLAP_THRESHOLD` is 0.6, and the separation was checked on both sides rather than assumed:
- Fixture true duplicate: **1.000**. Highest fixture near-miss: **0.221** (`motion-audit` and `knightcode-review-animations`).
- Across all 3,828 real pairs in the live 88-skill catalog, the highest score is **0.514**, `knightcode-context-save` and `knightcode-context-restore`, a deliberately complementary pair, not a duplicate, and correctly below the line. Next highest are 0.400 (`ios-fix`/`ios-qa`) and 0.385, all legitimately distinct.

So 0.6 sits in a real gap between the highest genuine pair (0.514) and an actual duplicate (1.000). Result on live data: **zero `overlaps` edges and zero `duplicates` edges across 88 skills**, which is the correct answer, there are no true duplicates left in the catalog now that source trees are no longer indexed as skills.
