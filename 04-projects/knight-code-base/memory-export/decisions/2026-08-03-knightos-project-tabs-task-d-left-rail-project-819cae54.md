# Decision: KnightOS Project Tabs Task D (left rail, project switcher UI) is complete: built, tested, and review...

## Decision

KnightOS Project Tabs Task D (left rail, project switcher UI) is complete: built, tested, and reviewed. Commit 53d6be2 on master. ProjectRail.tsx is the new vertical rail, listing every open Project and switching the existing horizontal channel strip + canvas to whichever one is active, with a per-Project color-cap picker matching the channel-tier swatch mechanism (Task 9). TerminalPane's own unmount no longer closes the real backend pty (that call moved to App's closeTabNow, the one place a channel is genuinely, permanently closed), since a Project switch now legitimately unmounts a channel's terminal UI without the channel itself closing. A remounted pane replays a full xterm.js screen snapshot (via SerializeAddon, a new dependency) taken at its last unmount, plus any raw pty output buffered while its Project was backgrounded, so switching back looks exactly as left and nothing that happened while away is lost, satisfying section 5.4 of the Project Tabs spec (the backend must not be interrupted by a Project switch).

## Rationale

All 6 of Task D's acceptance criteria are met and verified: the rail lists every open Project; clicking switches the strip+canvas to that Project's own channels; repeated switching with 2+ channels per Project running distinct commands produces zero state bleed; only the active Project's channel components and xterm.js instances are mounted at any time (confirmed via Playwright DOM-count assertions, not just visual hiding); Ctrl+Shift+T after switching Projects and back restores current state; a Playwright companion (e2e/project-switcher.spec.ts, 4 specs) proves an inactive Project's channels are genuinely absent from the DOM. A two-axis code review (Standards + Spec) ran against the diff and found two real issues before this was considered done, both fixed and re-verified: (1) a hard Standards-axis bug, ProjectRail reused ShopRail's swatch markup but the diff's own CSS never gave `.swatch` dimensions outside `.tool`'s ancestor scope, so the color cap would have rendered invisible on the new rail; fixed by widening the existing rule to `.tool .swatch, .project-chip .swatch` rather than duplicating it. (2) a real Spec-axis gap: a fresh xterm.js instance on remount only replayed output that arrived while backgrounded, losing whatever was already on screen before the switch, which fails the spec's own "exactly as last left" wording; fixed by adding `@xterm/addon-serialize` and a screen-snapshot mechanism (store on unmount, consume on remount, before replaying buffered live output), verified end to end by an e2e test that marks 4 distinct channels across both Projects, switches away and back repeatedly, and confirms every marker is still exactly where it was left with zero cross-Project bleed. Full verification: typecheck clean, 176/176 Vitest (5 new for the background-output buffer's bounded-append helper), 35/35 Playwright e2e clean on a full serial run (three unrelated, pre-existing tests each flaked once across repeated full-suite runs under sustained load on this machine, git-status.test.ts, drag-reorder-tabs.spec.ts, and app-menu.spec.ts's Open Project test, none touched by this diff, each confirmed passing cleanly in isolation, the same environmental-flake pattern already documented from the Task 10 merge).

## Alternatives Considered

Keeping the xterm.js Terminal instance alive across a Project switch instead of disposing it (rejected): would satisfy "exactly as last left" for free, but directly violates Task D's own explicit acceptance criterion that switching away must genuinely dispose each channel's xterm.js instance, a real resource-management requirement, not an implementation detail. Truncating the background-output buffer and any screen snapshot by a single shared character-count cap (rejected): a full serialized scrollback can be far larger than a live output chunk, and truncating raw text by character count risks slicing through the middle of an ANSI escape sequence and corrupting the replay; used SerializeAddon's own `scrollback` option instead, which bounds output at the line level, the same way the live terminal itself is already bounded. Extracting the swatch-trigger button (not just the popup) into a third shared component alongside ColorPicker and keyboard.ts (considered, deferred): flagged by the Standards review as a minor, judgement-call duplication across exactly two call sites; left inline rather than over-abstracting a small embedded control for now.
