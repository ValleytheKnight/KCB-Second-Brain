## Decision

omarchy-image-theme: full system-review pass against real Omarchy internals (per Chris's hard stop pending this review). Read the full theme lifecycle end to end: omarchy-theme-set, omarchy-theme-set-templates, omarchy-theme-list, omarchy-theme-install, omarchy-theme-remove, omarchy-theme-refresh, omarchy-theme-update, omarchy-theme-current, omarchy-theme-dir, omarchy-theme-color (mode resolution), omarchy-theme-switcher (the real picker), omarchy-theme-bg-set/omarchy-theme-bg-cache, omarchy-theme-set-keyboard, omarchy-theme-set-vscode, omarchy-hook, plus real theme directory contents (tokyo-night, flexoki-light official; together, howls-moving-castle user-installed) and Chris's own ~/.local/bin/omarchy-theme-from-image. Key findings, none yet applied to the plan or mockups pending coordinator reconciliation: (1) real theme format has far more optional fields than colors.toml + backgrounds/ (icons.theme, keyboard.rgb, vscode.json, neovim.lua, shell.lock.toml, preview.png, preview-unlock.png, unlock.png, chromium.theme), all preserved as-is by omarchy-theme-set's staging copy, meaning the general theme editor's save-in-place must not clobber them, this was never addressed in the plan. (2) The real picker (omarchy-theme-switcher) sources each theme's thumbnail from a static preview.png/jpg/etc. file shipped in the theme's own folder, falling back to the first backgrounds/ image if absent, never generating anything live; no omarchy tool auto-generates preview.png, confirmed by reading omarchy-dev-theme-preview (a terminal-only ANSI previewer, not an image generator). A theme this app creates ships no preview.png, so it will show the plain wallpaper as its picker thumbnail, not the tinted terminal-chrome look now mocked on the Selection screen. (3) mode = "light"/"dark" is a first-class colors.toml field with a real fallback cascade (mode key, legacy theme_type key, a light.mode marker file, background-luminance auto-detect, else dark), confirmed live against both a dark (tokyo-night) and light (flexoki-light) official theme. The wallust template this session already built (~/.config/wallust/templates/omarchy-colors.toml) emits no mode key at all, so every app-generated theme falls through to the luminance auto-detect, never decided explicitly. (4) The collision guard as scoped ("applies to creating a theme under a name that already exists in ~/.config/omarchy/themes/") only checks the user themes path; omarchy-theme-set's own staging logic copies the OFFICIAL packaged theme first (from /usr/share/omarchy/themes/) then overlays the user's theme of the same name on top, so naming a new theme "Nord" or "Gruvbox" (both real installed official themes on this machine) collides with the packaged tree in a way the current guard never checks, and would splice this app's colors.toml onto that official theme's other real files (icons.theme, keyboard.rgb, preview images) rather than either overwriting cleanly or being caught by the guard. (5) Applying a theme (omarchy theme set) is a wide-blast-radius operation: retints and restarts ~15 real subsystems in parallel (terminal, hyprctl, btop, opencode, helix, foot, tmux, gnome, pi, claude, browser, vscode, obsidian, keyboard RGB, wezterm), runs every non-sample script in ~/.config/omarchy/hooks/theme-set.d/ (5 real ones exist on this machine right now: voxtype install, 2 wezterm reapply scripts, agent setup, fingerprint setup), and can install a VS Code extension over the network as a side effect (omarchy-theme-set-vscode). None of this is a contradiction of anything decided, since the plan already treats omarchy theme set as an opaque shelled-out black box, but it means every real Save-and-Apply click in this app is heavier and more disruptive than the mockups visually suggest. (6) Re-invoking theme-set on an already-active theme (which the general editor's in-place Save effectively does) cycles that theme's background to the NEXT image in its backgrounds/ folder rather than reapplying the same one, a real, undecided side effect for multi-wallpaper themes. (7) Confirmed via 2 of Chris's own real sparse user themes (together, howls-moving-castle: colors.toml + backgrounds/ only) that a minimal theme with none of the optional files is already a normal, fully supported case in real Omarchy, not a special or broken one.
