# Isolated the decision_log rejection anomaly, three free-text fields is the trigger

Reproduced live what an earlier E2E verification pass could not. The same decision and rationale text, unchanged, succeeded with two free-text fields populated and failed with three. Adding alternatives_considered back in was the only change between the two calls. Confirmed the guard was not misreading real content, the source text sent in that call carries no literal tool-call marker anywhere, so whatever it saw was introduced somewhere between the call being made and the guard scanning it.  This rules out the two working theories tried earlier today: it is not raw text length (a 230-word, three-field call failed while a 600-word, two-field call succeeded during the E2E pass), and it is not apostrophes or punctuation in the content (identical text either side of the pass/fail line). The variable is specifically the count of populated free-text fields decision_log joins together before scanning.  This is not a guard bug and very likely not fixable inside this repo at all. It matches the exact failure shape the guard was originally built to catch, real parameter-boundary corruption in a multi-field tool call, the same class of defect that produced the twenty-one corrupted decision records that motivated building this guard in the first place. That corruption happens before the server ever receives clean text, so there is no server-side code to fix, the guard is doing its job correctly by rejecting it rather than storing something silently broken.  Practical guidance until this gets a real fix upstream: a decision needing a genuinely substantial alternatives_considered writeup should either fold that content into rationale as one field instead of three, or be split across two calls. Do not keep retrying a rejected multi-field decision_log call with cosmetic rewording, since the trigger is structural, not content-based, and rewording will not help.
