# KnightOS audited against the vendored React performance reference, one real fix applied

Ran the newly vendored 70-rule react-performance-rules.md against KnightOS's real renderer and main-process source, as a live test of whether the reference is actually useful rather than a speculative pass. Excluded the 13 rules already tagged dormant (Next.js server / RSC / SSR hydration, SWR remote fetching), correctly inapplicable since KnightOS is a pure client-side React 19 renderer inside Electron with data over IPC, not HTTP.  Checked all applicable rules across categories 1 (waterfalls, generic parts), 2 (bundle size), 4 (client-side, minus SWR), 5 (re-render optimization), 6 (rendering, minus hydration), 7 (JavaScript performance), and 8 (advanced patterns) against every renderer component (App.tsx, ShopRail.tsx, TerminalPane.tsx, EmptyState.tsx, CloseConfirmDialog.tsx, KnightOsMark.tsx, main.tsx) and the main/preload process files (terminal.ts, terminal-manager.ts, index.ts, api.ts, preload/index.ts, shared/ipc.ts, logging.ts).  Found one real violation: App.tsx's closeTabNow read activeTabId from closure instead of using setActiveTabId's functional form, forcing closeTabNow (and downstream handleCloseTab, passed to ShopRail) to be recreated on every active-tab change, exactly the stale-dependency pattern rule 5.11 (Use Functional setState Updates) warns against. Fixed by moving the active-tab fallback logic inside a functional setActiveTabId update nested in the existing functional setTabs update, so closeTabNow now has an empty dependency array and a stable identity for its whole lifetime.  Everything else checked came back compliant already, several by what reads as deliberate design (the single shared onData listener in App.tsx already matches rule 4.1's dedup pattern with its own comment explaining the prior N-listener version it replaced; outputHandlers and closeChecksInFlight already use useRef for transient values per rule 5.15; no useMemo/memo/localStorage/barrel imports/layout-thrashing patterns exist anywhere in the codebase to violate their respective rules). The codebase is small and deliberately built one vertical slice at a time, which likely explains the low defect rate: there simply isn't much surface yet for these patterns to have crept into.  Verified via npm run typecheck (clean) and npm run test (21/21 passed) after the fix, in KnightOS's own repo.
