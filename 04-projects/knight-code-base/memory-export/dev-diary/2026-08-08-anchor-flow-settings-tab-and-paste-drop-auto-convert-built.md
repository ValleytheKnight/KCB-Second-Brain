# Anchor Flow: settings tab and paste/drop auto-convert built

Built the last locked-scope gap on Anchor Flow: the settings tab (default position, default width, auto-convert-on-paste toggle), plus real behavior behind all three, not just stored-but-inert values.  Settings data model added to types.ts (AnchorFlowSettings, DEFAULT_SETTINGS), loaded/saved via the standard loadData/saveData pattern in main.ts (loadSettings/saveSettings). settings-tab.ts follows Linked Text Styles' existing settings-tab shape: sentence case, no top-level heading, three Setting rows (dropdown, text, toggle).  Default position/width now feed the manual toolbar directly: opening the toolbar on an image with no anchor state yet (readAnchorState returns null) pre-fills from settings instead of the old hardcoded DEFAULT_ANCHOR_STATE constant, which was removed in favor of one source of truth.  Auto-convert-on-paste required real design work, not just a UI toggle, since it's part of the locked v1 scope ("a settings toggle can switch pasted/dropped images to auto-float"). Considered and rejected: intercepting editor-paste/editor-drop with preventDefault() and reimplementing Obsidian's own attachment-creation logic (folder resolution, collision-safe filenames) myself, real untested surface area with a real risk of breaking normal pasting for every user if wrong, exactly the kind of DOM/editor-integration risk this account's rules call for a disposable risk test before building, and no risk test has been run for paste/drop interception specifically.  Built instead: a non-intercepting design. editor-paste/editor-drop handlers (checking evt.defaultPrevented first, in case another plugin already handled it) only arm a pending conversion context (editor plus source path) when the setting is on and the pasted/dropped payload contains an image file; Obsidian's own default handling runs completely untouched, creating the attachment and inserting its embed exactly as it always would. A vault 'create' event for a matching image file consumes the pending context (expires after 4 seconds so a create long after a paste is never mistaken for it), waits 50ms for Obsidian's own insertion to land, computes the exact expected embed text via FileManager.generateMarkdownLink (the same API Obsidian's own core paste handling would produce, so this doesn't have to guess at the user's link-format setting), searches the editor for that exact string, and replaces it with the anchor-managed tag using the default position/width. If the expected string isn't found for any reason, it silently does nothing, so a failed match still leaves the user with a completely normal, working image embed, never a broken paste. This mirrors the same coexistence philosophy already locked for the toolbar itself (never risk breaking Obsidian's own native behavior to add this plugin's own).  The pure logic (image-file detection, image-extension check, the pending-conversion arm/consume/expiry class) lives in auto-convert.ts and is unit tested (7 new tests, 29 total passing). The event-wiring itself (editor-paste/editor-drop/vault-create registration, the 50ms timing assumption, the generateMarkdownLink string match) is DOM/vault-dependent and untested, same judgment call already made for the rest of this project's interaction layer (toolbar-view.ts, main.ts) and for Linked Text Styles' own settings tab. This is flagged explicitly, not glossed over: the auto-convert path has NOT been risk-tested live the way toolbar selection detection was before it got built for real, and the 50ms delay is a pragmatic timing assumption, not something confirmed against Obsidian's actual insertion timing. Real manual verification (pasting or dropping an actual image with the toggle on, in the shared Plugin Tester vault) is still needed before trusting this in practice.  npm run lint: 0 errors (two new expected warnings, both understood trade-offs: obsidianmd/editor-drop-paste's preventDefault() suggestion, deliberately not followed since this design depends on Obsidian's own default handling running; and obsidianmd/settings-tab/prefer-setting-definitions, the declarative-settings-API trade-off, logged as its own decision). npm test: 29 passing. npm run build's tsc step throws the same already-confirmed-harmless TS2688 'diff' type-definition false negative every other project on this account hits; esbuild run directly produced a valid main.js. Hygiene re-checked clean: bin/knight-banned-language-check across every new/changed file, plus a direct real-name/email grep, both clean. Two commits made locally, not pushed, per the standing rule.
