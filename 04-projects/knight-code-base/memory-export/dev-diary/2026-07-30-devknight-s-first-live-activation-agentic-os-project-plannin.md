# DevKnight's first live activation: agentic-OS project, planning-phase protocol test

Chris said "activate devknight" and asked it to start planning a brand new native Windows application, described only as "a UI/UX/GUI Windows application that works as an agentic OS," with the explicit instruction to follow DevKnight's own defined protocol end to end as a real first live test, and to flag anything that does not work as designed rather than papering over it.  Session-start verification (step 1): dotnet 9.0.316 confirmed. MSVC 14.44.35207 confirmed under VS2022 Community's VC/Tools/MSVC path. Windows SDK 10.0.26100.0 confirmed. VS2022 Community 17.14.37516.0 confirmed with both NativeDesktop and ManagedDesktop workloads via vswhere. One real mismatch against the documented check: only a Community instance was found; no separate Build Tools instance exists on this machine, even though the checklist calls for verifying both are 17.14.37. This does not block native work (Community alone satisfies both required workloads) but is a real drift from what the check assumes, flagged rather than silently treated as passing.  Plugin verification: read the authoritative ~/.claude/plugins/installed_plugins.json directly (not the marketplace working tree, per the documented past mistake) and confirmed winui@win-dev-skills is pinned at 0.3.0, matching the cache directory. All 8 skill folders plus the winui-dev agent file physically exist on disk in the plugin cache. However, this session's actually-invocable Skill tool listing only exposed 6 of those 8 (winui-code-review, winui-design, winui-dev-workflow, winui-packaging, winui-ui-testing, winui-wpf-migration); winui-session-report and winui-setup were present on disk but not showing as invocable skills in this session. Flagged as a real discrepancy between installed-on-disk and exposed-as-callable, not silently assumed to be fine.  Decision/diary check (step 2): decision_search and dev_diary_search for "agentic OS" and "devknight" returned no prior record of this specific concept being scoped or decided. Three existing standing decisions cover DevKnight's own build (win-dev-skills adoption, the dedicated Obsidian vault, the completed build spec) but none touch this new project idea, confirming it is genuinely new scope rather than something to re-derive from memory.  Obsidian connection check (step 3): claude mcp list shows obsidian-workshop (the DevKnight Workshop vault, port 27123) as Connected, but no tools under that server name are actually callable this session (confirmed via ToolSearch). The only vault-editing tools present are under lorebrain-vault (port 27126), and calling vault_list against it returned the ROTFG D&D campaign vault's contents, not DevKnight Workshop's, i.e. a completely different vault. Recorded as a learning (see learnings_log key obsidian-workshop-mcp-connected-but-no-tools). Fell back to direct filesystem Read/Write/Edit against the real DevKnight Workshop vault folder on disk, confirmed reachable, and read workshop_management.md, Projects/_index.md, and the vault's templates directly that way.  Also found live: AskUserQuestion is not actually callable from inside this devknight subagent invocation (ToolSearch found no match), despite the dispatch instructions stating full tool access including it. Recorded separately (see learnings_log key askuserquestion-not-available-to-devknight-subagent). Open questions for Chris (project name/working title, what "agentic OS" concretely means, whether to scaffold the project now vs. hold at idea-note stage per the vault's own existing Protocol Whisper precedent, and whether running plan-ceo-review now is premature before the concept itself is scoped) were surfaced as plain text back to the primary agent instead, for it to relay and collect answers on, rather than guessed at or skipped.
