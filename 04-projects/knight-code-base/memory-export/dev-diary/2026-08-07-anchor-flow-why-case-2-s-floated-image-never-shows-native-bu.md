# Anchor Flow: why Case 2's floated image never shows native buttons at all

Follow-up question from Chris after the toolbar risk test correction: why does the floated raw img tag never show Obsidian's native zoom/view-code buttons anywhere, including the top strip where clicks correctly land on the real image. The click-target fix from the earlier correction explains why most of the image was unclickable, it does not by itself explain why the native buttons never render at all, even where clicks do reach the image.  Ran a clean, controlled four-way test at the top of the risk test note (guaranteed to render immediately, sidestepping both CodeMirror's viewport virtualization and Reading mode's lazy rendering, both of which produced misleading stale-DOM reads earlier in this same investigation): a raw img tag alone on its own line with no float class, the same with text right after it on the same line, and both of those again with the float class added. All four came back identical: none get Obsidian's `.image-embed`/`.embed-actions` wrapper, all four get routed through CodeMirror's generic `cm-html-embed` inline-HTML-passthrough wrapper instead.  This settles it: the native toolbar's absence has nothing to do with float, z-index, or text adjacency. It's a source-syntax fact. Obsidian only gives an image the full embed-widget treatment (and thus the native buttons) for its own `![[wikilink]]` embed syntax. A raw HTML img tag, the mechanism the float-wrap approach depends on for styling reasons found in an earlier risk test, never gets that treatment, regardless of what CSS is later applied to it.  One thing worth flagging for anyone re-running a similar DOM check on this note later: an earlier, single-case version of this test appeared to show a plain unfloated img tag DID get the embed wrapper, which looked like a real counterexample until traced down. That was a false match, both cmA's actual empty className and Case 1's own pre-existing native embed image also have an empty className, and a `find` on that alone can silently grab the wrong element. The four-way test used explicit marker classes specifically to avoid this.
