# KnightOS Project Tabs Task D built, reviewed, and verified

Built Task D (left rail, project switcher UI) end to end this session, commit 53d6be2.  ProjectRail.tsx is the new vertical rail: one chip per open Project, click switches App's activeProjectId, active/idle visual state extends the exact same ember-glow language ShopRail already shipped for channels, applied one tier up. A per-Project color-cap picker reuses the same swatch mechanism channels already have (Task 9), which meant extracting two small shared pieces rather than duplicating them a second time: keyboard.ts (activateOnKey, Enter/Space activation) and ColorPicker.tsx (the popup itself), both now used by ShopRail and ProjectRail alike. Confirmed the extraction was behavior-preserving by rerunning the full existing e2e suite before adding anything new, all 31 pre-existing specs passed unchanged.  The real engineering problem Task D introduced: since App.tsx already only rendered the active Project's own tabs (tabs = activeProject?.tabs ?? []), the rail itself needed no new gating logic to satisfy "only the active Project's channels are mounted," that fell out of the existing derivation for free. But TerminalPane's own unmount cleanup unconditionally called window.knightos.terminal.close(tabId), which kills the real backend pty. Before Task D, unmount only ever happened when a channel was genuinely, permanently closed, so that coupling was invisible. A Project switch now unmounts a channel's TerminalPane without the channel closing, which would have silently killed a real running process (a dev server, a long build) the instant its Project went into the background, directly violating section 5.4 of the Project Tabs spec ("nothing about switching Projects should feel like it interrupted anything"). Fixed by moving the actual terminal.close call out of TerminalPane's cleanup and into App's closeTabNow, the one place a channel is truly done; TerminalPane's unmount now only ever tears down local UI resources (xterm instance, resize observer, output/action registrations).  That fix alone left a second, real gap a two-axis code review caught before this was considered done: a fresh xterm.js instance on remount starts blank, so a Project switch would only ever show whatever new output arrived while backgrounded (via a bounded per-tab output buffer, appendBackgroundOutput/BACKGROUND_OUTPUT_BUFFER_CHARS in tab.ts), losing everything that had already been on screen before the switch. That fails the spec's own "switches the strip + canvas to that Project's own channels exactly as last left" wording. Fixed with @xterm/addon-serialize (new dependency, latest stable 0.14.0): TerminalPane's cleanup now calls serializeAddon.serialize({ scrollback: SCROLLBACK_LINES }) right before dispose and hands the result to App's storeScreenSnapshot; a remount consumes that snapshot first, then any buffered live output, then resumes live. serialize()'s own scrollback option bounds the snapshot at the line level, avoiding the real risk a raw character-count truncation would have had of cutting mid-escape-sequence and corrupting the replay. storeScreenSnapshot is guarded against a genuine close: since React's own unmount fires asynchronously after closeTabNow's state update, a plain "delete then let the trailing unmount re-store" race would otherwise leak a snapshot for a tabId that's never coming back; the guard checks whether the channel still exists in any Project before storing.  The code review's Standards axis also caught a real, if smaller, bug: ProjectRail's swatch markup was copied verbatim from ShopRail (button + span.swatch), but the diff's own CSS only gave .swatch its dimensions under a .tool ancestor selector, so the color cap on the new rail would have rendered with zero size, invisible. Fixed by widening the selector to .tool .swatch, .project-chip .swatch rather than duplicating the whole rule block.  Verification, run repeatedly, not once: typecheck clean throughout. Vitest 176/176 (171 pre-existing plus 5 new, covering appendBackgroundOutput's normal-append and cap-at-the-tail-not-the-head behavior). Playwright e2e 35/35 clean on a full serial run, the new e2e/project-switcher.spec.ts (4 specs) proving: the rail lists both seeded Projects and switches the strip correctly; switching back and forth with 2+ channels per Project running distinct commands produces zero state bleed and every marker survives a round trip (the real, live proof the screen-snapshot fix works, not just that new output arrives); a channel's delayed output (Start-Sleep then Write-Host, triggered right before switching away) is not lost while its Project is backgrounded; and Ctrl+Shift+T after switching Projects and back reopens the right channel in the right Project, never bleeding into the other's close-history. Seeding two real Projects for these tests required writing a v2 session.json directly before launch (the same pattern session-persistence.spec.ts's own corrupted-file test already uses), since Task E's interactive New-Project control doesn't exist yet, this task deliberately stayed inside its own scope rather than reaching ahead into Task E's.  Three unrelated, pre-existing tests each flaked exactly once across several full-suite reruns under sustained load on this machine (git-status.test.ts's ahead/behind count test, drag-reorder-tabs.spec.ts, and app-menu.spec.ts's Open Project test), none touched by this diff; each confirmed passing cleanly in isolation immediately after, the same environmental-flake signature already documented from the Task 10 merge session.  Neither of the Project Tabs spec's two still-open questions (section 6: Project close-confirmation shape, cross-project command palette) became relevant during this task, both are Task E and Task G's own concern respectively. Task D's own scope stayed to listing, switching, and the mount/dispose/snapshot mechanics; creating, closing, reordering, and a project-aware palette are still Task E/F/G's jobs.
