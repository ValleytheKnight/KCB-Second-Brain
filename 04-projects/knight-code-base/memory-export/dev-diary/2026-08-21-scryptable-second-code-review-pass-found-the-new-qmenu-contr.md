# Scryptable: second code-review pass found the new QMenu contrast test itself was hardcoded, not a real regression guard

Second follow-up in the same session to the Import-dropdown-menu contrast fix chain (`0fac271` then `ef9cade`). Ran `/code-review` again against `ef9cade` per this repo's standing rule.  Three findings, treated differently on purpose:  1. Real, fixed. `tests/test_theme.py`'s disabled+selected WCAG check hardcoded its expected `(palette.surface, palette.text_secondary)` pair instead of reading the actual declared background/text out of `QMenu::item:disabled:selected`'s own rule. That meant the test would stay green even if that rule's background were changed back to `palette.primary`, the exact regression this fix chain exists to prevent, since the hardcoded pair never inspects what the rule actually says. Fixed by adding `_declared()`/`_effective_background()`/`_effective_text()` helpers that parse the real declared value out of each state's generated rule, falling back to `QMenu`'s own background or `QMenu::item`'s own text color when a state doesn't declare one, and resolving a literal `"transparent"` background to the menu's own surface (matching what actually renders). Added a direct assertion that the disabled+selected rule's background is literally `"transparent"`. Hand-verified the fix actually works as a regression guard: wrote a scratch copy of `theme.py` with that rule's background reverted to `palette.primary` (never committed), ran the rewritten test against it, confirmed it fails with the same ~1.05:1 Dark ratio the original review measured (2.49:1 Light), then deleted the scratch file.  2. Real, but out of scope, flagged rather than fixed. `#FirstRunContinueButton:disabled` (`background: {palette.border}`, `color: {palette.text_secondary}`) fails WCAG AA in the Light palette: 4.39:1, just under the 4.5:1 bar (Dark passes at 5.26:1). Unrelated code (the First-Run wizard's continue button), predates this session, would be scope creep on a task specifically about the Import dropdown. Left for a future small fix, recorded in the vault so it isn't lost.  3. Reviewed, no action, disagreed with the framing. The review called the compound rule's explicit `color: {palette.text_secondary}` line unnecessary since the current `:selected`/`:disabled` declaration order already resolves to that color without it. True only as an accident of today's ordering. The entire point of using a compound `:disabled:selected` selector is to stop depending on declaration order (a compound selector has higher CSS2 specificity than either single-state selector), so declaring color explicitly there is what actually makes that guarantee hold if the two single-state rules are ever reordered. Kept as written.  Committed and pushed as `07544ea` to `https://github.com/ValleytheKnight/Scryptable` (master). 145/145 tests pass (same two test functions, rewritten rather than added to). Third `/code-review` pass launched against this commit to close the loop.  Updated the DevKnight Workshop vault: a third follow-up subsection in `Projects/Scryptable/06 Lessons Learned/Task 7 Diarization Integration Build Notes.md` (also removed a stray duplicated sentence left over from an earlier edit pass), `00 Overview.md` Continuation Point (now references all three commits, plus the flagged FirstRunContinueButton gap as its own bullet), and `Projects/_index.md`'s Scryptable one-liner.
