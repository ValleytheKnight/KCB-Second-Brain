# Anchor Flow: fixed rapid multi-paste filename collision, built Chris's manual test walkthrough

Continued from the prior dispatch's risk test, which found a real, reproducible bug: pasting two images back to back with no delay broke auto-convert for the second one. Root cause was already confirmed going in (Obsidian's own attachment naming has one-second granularity, so two rapid pastes collide on the same generated filename and only one vault create event fires).  Fix: PendingAutoConvert (src/auto-convert.ts) was a single-slot holder, arm() overwrote whatever was previously armed. Replaced it with a real queue: arm() pushes, a new peekAll() returns every still-unexpired armed context without removing them, and remove(context) drops one specific context once it actually converts something. main.ts's consumeAutoConvert now snapshots every currently-armed context when a matching create event fires (not just one), and after the same 50ms settle delay loops over all of them, re-reading editor.getValue() fresh on every attempt so converting one candidate's offset shift doesn't corrupt the search for the next.  Rebuilt from source, redeployed to the shared Plugin Tester vault, reloaded the plugin, confirmed no load errors, then retested with the same real-dispatched-paste methodology as the original risk test (a real File from real bytes, wrapped in a real DataTransfer, dispatched as a genuine ClipboardEvent on the CodeMirror content DOM). Two rapid pastes with distinct bytes: both converted, confirmed only one file was created (the collision reproduced) and both embeds picked up the anchor-managed tag. Three rapid pastes: same result, confirming the fix generalizes beyond the original two-paste case. One run (two rapid pastes with identical bytes) initially looked like a fresh failure, neither embed converted on the first read, but an instrumented rerun showed the queue going 0 to 1 to 2 correctly on arm and draining back to 0 with both converted after the settle delay; a later re-read of the first run's own note section showed it had, in fact, converted too, just after my first check rather than within it. Since no other create event exists for that file, the only explanation is the same original window.setTimeout(50ms) callback firing later than 50ms wall-clock in a renderer busy from rapid successive CLI eval calls, the same Electron/Chromium timer-throttling category already documented in this project's own history, not a plugin defect, and arguably a point in the fix's favor since the queue does not discard a context after one failed look the way the old design effectively did.  Unit tests rewritten for the queue API (8 tests covering arm/peekAll/remove/expiry/multiple-simultaneous-arms), full suite 33 passing, lint 0 errors (same two pre-existing accepted-tradeoff warnings), esbuild produced a valid main.js. Committed locally (6baa096), not pushed, per the standing rule.  Built Chris's own hands-on test walkthrough: Anchor Flow Manual Test/Anchor Flow Manual Test.md in the shared Plugin Tester vault, three numbered parts (toolbar float/position/resize, the settings tab and its pre-fill behavior, auto-convert-on-paste including an explicit rapid-double-paste and rapid-triple-paste break-it test with a plain-language explanation of what used to fail and why), concrete steps and expected-result callouts throughout, a reset-to-defaults closing section, and a checklist.  Real incident mid-session, worth recording plainly: two Obsidian main-process-adjacent crash dialogs surfaced during this dispatch (JSON.parse failures in the app's own CLI socket handler, Socket.n in main.js). The first, from a prior dispatch, was already root-caused to a bash backtick triggering command substitution inside a double-quoted string. This second one had a different malformed tail and surfaced from a PowerShell-issued call, meaning the first fix addressed one triggering case, not the underlying class of bug. Per Chris's own instruction mid-dispatch, stopped using the obsidian CLI's socket-based commands for the remainder of the session (one accidental read-only CLI call slipped through immediately after the instruction landed, caught and flagged rather than silently continued), switched entirely to direct file read/write for the rest of the test-note authoring and all verification. Confirmed the app itself stayed alive and responsive throughout (all Obsidian.exe processes Responding: True, no process restart at a suspicious time), and vault/plugin state was intact by direct file read both times. Full pattern, working hypothesis, and confidence level logged via learnings_log rather than repeated here.
