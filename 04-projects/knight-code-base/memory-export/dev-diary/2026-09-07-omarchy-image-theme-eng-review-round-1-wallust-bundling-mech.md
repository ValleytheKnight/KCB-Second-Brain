# omarchy-image-theme: Eng Review Round 1, wallust bundling mechanics resolved to a two-option gate

Ran Phase 3 (Eng Review) of formal-dev-workflow for omarchy-image-theme. Read the accepted CEO plan, the closed Design Review deliverable, and the live Pencil canvas (confirmed still 10 frames, matching the design review's inventory, no drift).  Resolved the one carried Design Review concern (wallust bundling mechanics) by reading wallust's real Cargo.toml and README directly rather than assuming. Found it's a genuine dual lib+bin crate (published on crates.io as an importable library, `src/lib.rs` alongside `src/main.rs`), with a pure-Rust dependency tree (no ImageMagick/X11/pkg-config) and prebuilt static musl binaries on its Codeberg releases page. This means bundling has two real technically viable shapes: a Tauri sidecar binary (external process, same as the CEO plan's existing shell-out architecture) or an embedded library dependency (in-process calls into wallust's undocumented internal API). Recommended the sidecar approach because both already-built mockups (Missing Dependency, Apply Failed) model wallust as a subprocess with an exit code and stderr text, a locked Phase 2 design the embedded-library path would invalidate for a performance gain that doesn't matter at this call volume. This is the one item handed back to Chris as a gate question before the eng-review deliverable can close.  Resolved three further architecture items directly, no gate needed: (1) capability scoping for user-picked images/folders, real gap found in the CEO plan's own worked fs:allow-read example ($PICTURE/** can't express an arbitrary batch folder, and Tauri v2 has no documented "picker grants temporary scope" mechanism per its own file-system docs and a GitHub discussion on this exact gap), resolved by routing file I/O through custom Rust commands instead of the generic plugin-fs API, sidestepping the scope model entirely rather than reaching for a $HOME/** grant; (2) batch progress uses a Tauri Channel per tauri-dev's own guidance, not a blocking call; (3) wallust gets pinned to an exact version with its MIT license text bundled into the app.  Confirmed live that formal-workflow-gate.ts still blocks TODOS.md writes at phase "eng" (attempted the edit directly rather than reasoning from the hook's source alone; got the expected denial). The two v2-deferral TODOS.md entries (preview.png generation, general theme editor's extra-file preservation) are drafted in full inside the eng-review deliverable, ready to land once Task Breakdown completes or the workflow pointer is paused for this one unrelated maintenance edit.
