# KnightOS Project Tabs Task C built, reviewed, and verified

Built Task C (renderer state restructuring) end to end this session. App.tsx's flat tabs/activeTabId/gitStatusByTab/close-history state (previously separate useState calls at the top of the component) is now a per-Project structure: projects: ProjectState[] plus a single global activeProjectId. A new src/renderer/src/project.ts module holds the pure, JSX-free helpers this needed: ProjectState itself, toPersistedProject/toPersistedTab (the save-side reduction), buildRestoredProject (the load-side construction, always defaulting a restored Project's activeTabId to its first channel per the spec's own "not persisting per-project activeTabId" rule), createProjectFromTab (lazily seeds the very first Project the first time a channel is ever opened, since Task E's real New-Project control doesn't exist yet), resolveActiveProjectId (prefers the file's own persisted activeProjectId on restore, falls back to the first Project if that id no longer names a real one), findProject (a tiny named stand-in for a two-level projects-then-tabs reach), and a per-project close-history mechanism (ClosedHistoryByProject, recordClosedTabForProject, popMostRecentClosedTabForProject) proving in a real unit test that closing channels in one Project can never surface when reopening in another.  The session IPC contract changed too, per decision 31a4407c's own deferral: session.load/session.save (src/shared/session.ts, src/main/session-store.ts, src/preload/api.ts, src/main/index.ts) now carry the full SessionFile (every Project, not just the active one), since the renderer is now the one holding the full multi-project picture rather than main silently picking one Project on its behalf. session-store.ts got materially simpler as a result: the old activeProject()-merge logic is gone entirely, saveSession now just writes whatever full file the renderer hands over.  Two real issues surfaced and were fixed before considering the task done, each its own commit:  1. A /simplify pass caught that the save effect depended directly on the projects array, which now also carries fields that were never meant to trigger a save (activeTabId, gitStatusByTab), so an ordinary tab switch or a background git-status tick was silently triggering a full session save and atomic disk write that never happened in the original flat-state version (that version's save effect depended only on tabs, never on the separate activeTabId state). Fixed by keying the effect on JSON.stringify(projects.map(toPersistedProject)) instead of the raw projects reference, restoring the original behavior: only a real, persisted change re-triggers a save.  2. A two-axis /code-review (Standards axis DONE_WITH_CONCERNS, Spec axis clean DONE) flagged a redundant ref-mirror pair: tabsRef/activeTabIdRef were re-deriving exactly what projectsRef/activeProjectIdRef, already kept current for other callbacks, already gave directly. Fixed by adding findProject(projects, id) and removing the redundant pair, which also gave a name to the two-level project-then-tab reach in closeTabNow the same review flagged as an unnamed message chain.  Verification: full Vitest suite green (150 to 153 tests, the 3 new ones covering findProject), full Playwright e2e suite green (26 specs, --workers=1), including app-menu.spec.ts which directly exercises the refactored menu-action listener. Typecheck clean throughout. All four of Task C's own acceptance criteria confirmed: single-Project behavior identical to before (proven by the unmodified e2e suite), main process's terminal/pty registry untouched, reopening always reads the active Project's own close-history fresh at call time from refs, and the per-project close-history map never leaks across Projects (proven directly in project.test.ts). Neither of the Project Tabs spec's two still-open questions (close-confirmation shape, cross-project command palette) became relevant during this task, both are Task E/G concerns.
