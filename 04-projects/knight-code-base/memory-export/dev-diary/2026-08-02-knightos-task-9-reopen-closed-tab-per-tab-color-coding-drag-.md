# KnightOS Task 9: reopen-closed-tab, per-tab color coding, drag-to-reorder

Built Task 9 for KnightOS (decisions 223601d5, 9f55565d): a Ctrl+Shift+T shortcut reopens the most recently closed tab, walking back through an in-memory, 10-deep close history rather than just the single last close; the session schema's already-present `color` field is now wired to the shop rail's swatch through a small popover picker, replacing the old hash-derived color the rail previously fell back on; and tabs drag-to-reorder in the strip via native HTML5 drag-and-drop.  Followed the project's established pattern (check Task 7/8 before writing code): the color field and its closed-set TabColor type already existed in src/shared/session.ts, unused since Task 7; reused directly rather than reinvented. Reopen history and reorder both needed new pure, JSX-free helpers in tab.ts (recordClosedTab/popMostRecentClosedTab, reorderTabs, moveTabByOneStep), matching the existing convention that testable logic lives outside .tsx files.  Two real things worth remembering for next time. First, a real StrictMode trap: recording a closed tab's data into an in-memory ref has to happen outside any setState updater function, not inside one, since React's dev-mode double-invoke of updater functions would double-record it; the clean fix is a `tabsRef` mirror (a ref kept in sync with state via a plain effect) rather than threading the lookup through every caller's own closure. Second, a real semantics trap in reorderTabs: "insert the dragged tab immediately before its drop target" (the natural rule for an arbitrary mouse-drop position) does NOT reduce to a same-position no-op the way "swap with a neighbor" does for a one-step keyboard move; a keyboard-driven one-step reorder needs its own plain adjacent-swap function (moveTabByOneStep), not a reuse of the drag-drop insert-before logic, they only look interchangeable at first glance.  A `/simplify` pass and both `knightcode-code-review` axes (Standards, Spec) ran before committing. Standards axis found 3 real, applied issues (task-number citations in source comments where the codebase's real convention is a durable decision-ID citation instead; the stale-closure/tabsRef fix above; the combined e2e spec file split into 3 per-feature files to match this project's established one-file-per-feature naming convention) plus one real accessibility gap: ShopRail.tsx's own docstring already promised every clickable rail control answers Enter/Space, and drag-to-reorder shipped with no keyboard path at all, a direct contradiction of a bar the same file states about itself, not just general accessibility debt. Fixed with a Ctrl+Left/Right one-step reorder, verified live via Playwright that a moved tag keeps real DOM focus across repeated presses. Spec axis came back clean; one small scope call surfaced for Chris to confirm explicitly rather than let sit assumed: the acceptance criteria said "a color or icon" per tab, only color was built, already grounded in DESIGN.md and the existing schema field, not a gap.  105/105 Vitest (20 new), 19/19 Playwright e2e (6 new, one file per feature per the fix above) passing clean.
