# Anchor Flow toolbar risk test: root cause behind two real-click discrepancies

Chris clicked through the Toolbar Selection Risk Test note by hand and found two problems the earlier synthetic-click test had wrongly called a clean pass.  Case 1, plain wikilink embed: Obsidian's native embed toolbar showed up next to our own. The real mechanism, found by reading the live app's actual stylesheets rather than the obsidian.asar on disk (which turned out to be stale relative to the running process): a hover-based CSS rule and a click-based CSS rule both reveal that native toolbar independently. Our click-based suppression only ever reached the click-based one. The hover rule is pure CSS, tied to real cursor position, invisible to any JS event including a synthetic one, which is why the earlier automated test never caught it. The working countermeasure was a plugin-owned stylesheet rule with a higher-priority declaration, scoped to a marker class on the specific embed being managed, verified live to hold even when the click-based state was forced true directly.  Case 2, an already-floated raw img tag: the toolbar only responded on the top slice of the image, the rest of its area routed clicks into the wrapped paragraph text instead. Found via elementFromPoint hit-testing at several heights down the image: CodeMirror's line boxes for the wrapped text always span the full editor width and sit later in the DOM than the floated image, so they win the browser's default hit-test priority anywhere they overlap it. Giving the floated image its own stacking context resolved this, confirmed by the same hit-test method across the whole image afterward, with no change to the surrounding text's own clickability. The absence of native buttons for this case needed no fix, a plain img has no embed wrapper for that native CSS to target at all.  Both fixes verified live in the Plugin Tester vault. Full detail in Obsidian Shipped and Roadmaps.md's Anchor Flow entry.
