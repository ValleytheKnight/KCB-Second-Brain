# KnightOS folder-picker root cause: stale packaged build, not a code bug, plus a native application menu

Two ad hoc pieces of work for KnightOS, both requested directly by Chris, outside the numbered Milestone 1 task sequence.  Task A: Chris reported being forced to pick a project folder on every launch, despite Task 7 shipping session persistence. Root-caused, not guessed. Read the real startup path (App.tsx's restore effect, session-store.ts's loadSession) and confirmed it byte-identical against HEAD: current source already restores saved tabs silently on launch and only shows the picker at zero saved tabs or an explicit open-project action, exactly as Task A asked. So the bug wasn't in the code. Traced through %APPDATA%\knightos\logs\main.log that real interactive launches never wrote a session file to ~/.knightcode/knightos/, and that directory didn't exist on disk at all. Resolved Chris's real Desktop shortcut (KnightOS.lnk, via a live PowerShell WScript.Shell COM call) to dist/win-unpacked/KnightOS.exe, a packaged build from July 31 02:36, about 22 hours before Task 7 landed in source at commit 21c6560 on August 2 00:22. Every real launch through that shortcut ran a build with zero restore logic ever built into it. Confirmed by extracting the old app.asar and finding no session-related code inside it at all.  The fix was not a source code change, because none was needed: rebuilt the package (npm run package), verified the new app.asar actually contains today's code (grepped for knightos:menu-action and the current session logic), then launched the real rebuilt exe directly and confirmed ~/.knightcode/knightos/session.json was created on disk for the first time ever, correct shape. Added 2 new Playwright e2e tests naming both required paths explicitly (fresh install shows the picker, restart with a saved session never does), per Task A's own instruction to cover both.  Flagged, not silently fixed: nothing in this project currently keeps dist/win-unpacked current after a task lands, so the shortcut will go stale again after the next task unless repackaging becomes a standing step, or Task 10's auto-update changes the shape of the problem. Logged in TODOS.md. Also found and logged a separate, unrelated collateral issue while investigating: electron-log's Node-only fallback path resolution writes Vitest test-run noise into the same real production log file a live launch uses, which briefly looked like real evidence before the timestamps and message shapes were checked against what session-store.test.ts actually triggers.  Task B: added a native Electron application menu (File, Edit, View, Help). Every item calls the exact existing renderer handler a keyboard shortcut or rail control already used (handleOpenProject, handleCloseTab, reopenClosedTab, openPalette, TerminalPane's existing Ctrl+C/Ctrl+V copy-paste), through one new one-way MenuAction IPC channel, no action logic duplicated. Real discovery that changed the approach: Task 8's "Tool Rack" command palette turned out to be a plain tab-switcher, not a general command registry the task brief assumed existed; there is no {id, label, handler} registry anywhere in this codebase, so menu items hang directly off App.tsx's real handler functions instead. Deliberate accelerator design: the two shortcuts that already existed (Ctrl+K, Ctrl+Shift+T) show their real binding in the menu as a display-only label (registerAccelerator: false) so Electron's native menu system never claims the keystroke away from the renderer's own already-tested capture-phase listener; brand-new items (Open Project, Close Tab, Copy, Paste) got no accelerator at all, deliberately, since KnightOS embeds a real terminal and several obvious candidate combos (Ctrl+W, Ctrl+O) are real shell/readline/vim bindings a native accelerator would silently steal before xterm.js ever saw them. A real Windows-specific bug was caught live during the build: Menu.setApplicationMenu has to run before createWindow(), not after, since a Windows BrowserWindow captures its menu bar at construction time and doesn't update retroactively; the symptom was the app showing Electron's own auto-generated default menu with no error anywhere, only caught by directly inspecting the real running menu structure via Playwright's electronApp.evaluate.  Both /simplify and both knightcode-code-review axes ran against the combined diff. Standards axis: PASS, verified compliant against docs/ELECTRON_SECURITY_CHECKLIST.md sections 2, 3, 4, and 7 specifically (minimum preload surface, IPC validation via a closed-union type guard, shell.openExternal/openPath both using only main-process-owned values never renderer input, DevTools menu item gated on app.isPackaged). Spec axis: FAIL on Task A specifically, and a legitimate finding, not a false positive, since the diff alone shows no code fix and the real fix (rebuilding a gitignored build artifact) leaves no trace in git at all; that gap is now closed by this entry and a matching Lessons Learned note, written after the fact, which is itself the real lesson: when a task's real fix is operational rather than a source diff, write the root-cause record before running a diff-only review, not after, since a diff review has no way to see an operational fix and will correctly flag its apparent absence. Task B came back clean on both axes.  Typecheck clean, 107/107 Vitest, all 26 Playwright e2e specs passing clean in a full serial run (--workers=1), no stray processes left running.
