# Artifact publish from a dispatched subagent does not durably register

While building KnightOS's Project Tabs Task A concept mockup, published an Artifact from inside a dispatched devknight subagent session (via the Agent tool, not the primary interactive session). The publish call returned a normal-looking success response with a real URL. Chris reported the link as "page not found." Investigated rather than assumed: called Artifact action:list (both default scope and scope:all, limit up to 25) and the just-published artifact was absent from the results entirely, even though it should have sorted first as the most recent. A second attempt to republish to the exact same file path (intended as an update, same URL) returned "the artifact you're updating was deleted, or you no longer have write access to it," confirming the first publish never actually persisted server-side despite the tool call itself succeeding.  All 10 real KnightOS artifacts that do show up in the list (Milestone 1 mockups, the north-star mockups, the tab-close-confirmation preview, the logo concept) are dated 2026-07-31, and per that day's dev-diary entries were built during ordinary interactive sessions, not dispatched subagent sessions. This lines up with the note already surfaced live in the same tool call's own response ("Live subscription: skipped, only an interactive or SDK main-loop session holds the watch, not a subagent, teammate, background, or print session"), suggesting artifact publishing generally, not just the live-subscription feature, may not durably register when called from inside a dispatched subagent context.  Not yet fully root-caused to a mechanism (no access to the publish backend), but the evidence is consistent and reproduced twice in the same session. Workaround used: handed the real mockup file path back to the coordinator/primary session so it (not this subagent) performs the actual publish. Flagging this as a real, likely-recurring gap for any future subagent (devknight or otherwise) that tries to publish an Artifact directly, the same class of limitation as the already-known AskUserQuestion-not-callable-from-a-subagent restriction.</body> <parameter name="tags">["devknight", "artifact", "subagent-limitation", "knightos"]
