# Scryptable eng review fully closed: both open items resolved and designed in whisper_app_design.pen, holding before Phase 3.5

Both of eng review's open items for Scryptable (protocol-whisper-app) are now resolved, and real design work followed through in the same session rather than staying as prose decisions.  Item 1 (Anthropic OAuth) was already resolved in the prior turn (decision a0875546). This turn: Chris asked for the actual OAuth toggle removed from whisper_app_design.pen and a real "run it locally" design added, plus a real MCP settings surface since none existed. Loaded get_guidelines (Design System, Web App) first, then worked directly in the .pen file via the pencil MCP tools.  Removed AuthMethodRow and OAuthNote from the AI Provider Settings dialog (J3bA5); Anthropic now shows the same plain API Key field OpenAI already had. Added a new "AI Provider Settings (Local or Custom Model)" state (q43wpL) with a real Endpoint URL field, an optional Model Name field, and a plain-language note naming Ollama/LM Studio only as examples of the category (per the standing no-OSS-tool-naming rule, decision d2eb656d, these are the user's own external tools, not something Scryptable wraps). Caught and fixed two text-wrapping bugs via screenshot verification (missing textGrowth: fixed-width on long descriptive text nodes caused clipped copy).  Found, by checking the LLM Handoff Session screen directly rather than assuming, that the only existing MCP-related UI was a passive status readout (McpStatusBar, "MCP: 2 tools connected"), no way to actually add, remove, or configure a server. Added a real "MCP" tab to Preferences (between AI Provider and Transcription) and a full "Preferences (MCP Tab)" screen (jJY9n): a connected-servers list with status badges and remove actions, an Add MCP Server button, and a toggle plus address field for Scryptable's own MCP server. Considered checking KnightOS's own mockup file for its MCP tab pattern as the coordinator suggested, decided against opening it, the connection-manager shape used here is a standard pattern that didn't need copying, and logged that reasoning rather than silently skipping the suggestion.  Item 2 (CUDA/CPU distribution) got resolved by Chris mid-task as a hybrid: explicit CUDA choice at install time, CPU-only default, a first-run GPU-detected upgrade prompt, and an in-app upgrade action for a later hardware upgrade (decision b0c17ad2). Designed the two genuinely in-app pieces: a "GPU Acceleration Available (Dialog)" (SkeTG, matching KnightOS's own elevated-terminal warning pattern with a don't-ask-again checkbox) and a "Transcription and Diarization Settings (CPU, Upgrade Available)" state (e6euEe) adding a real "Install GPU Acceleration" action below the existing Device field. Deliberately did not design an in-app screen for the explicit install-time package choice itself, reasoned from the CEO review's actual packaging decision (PyInstaller --onefile, no installer wizard yet) that this is a download-page concern, not part of this app-mockup file, and logged that reasoning rather than assuming every option needed an app screen.  Both eng review items are now fully closed, with real design artifacts, not just decision text. protocol-whisper-app-eng-review.md and the vault's Scryptable/00 Overview.md and _index.md all updated to reflect this.
