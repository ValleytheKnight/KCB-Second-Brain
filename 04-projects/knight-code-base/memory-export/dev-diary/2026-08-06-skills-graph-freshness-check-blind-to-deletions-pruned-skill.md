# Skills graph freshness check blind to deletions, pruned skills stayed resolvable

Found while running a real skill install/prune cycle end to end (bun run skills:install, then --prune) as part of an infrastructure verification pass. After pruning a throwaway skill, knightbrain_query mode:skills still resolved it, pointing at a SKILL.md file confirmed absent from disk.  Root cause: lorebrain/src/freshness.ts's ensureFresh compared only the newest input mtime against the stored graph's own mtime. A deletion never produces a mtime newer than the last build, since the file removed no longer contributes a timestamp at all. The newest mtime among what remains can only stay the same or drop, so "is any input newer than the graph" can never be tripped by a pure deletion. The graph then answers queries with content that no longer exists until an unrelated add or edit elsewhere happens to move the newest mtime past the graph's build time, at which point the deletion is picked up only as a side effect of that unrelated rebuild.  Fixed by adding a second signal alongside mtime: a count of the skills-mode input files discovered on each freshness check, stored on the graph as a new inputFileCount field and compared on the next check. A count mismatch (in either direction) now forces a rebuild even when the newest mtime hasn't moved. Old stored graphs have no inputFileCount, so they mismatch automatically on first check post-upgrade and rebuild once, the same self-healing pattern inputShape already uses for the source-set change it backstops.  lorebrain/src/types.ts: added KnowledgeGraph.inputFileCount (skills mode only). lorebrain/src/freshness.ts: renamed newestSkillsMtime to skillsInputStats (now returns {newest, count}), added ensureFreshSkills as skills mode's own freshness path instead of routing through the generic mtime-only ensureFresh, wired into ensureFreshGraph.  Proven with two new regression tests in test/skills-freshness-deletion.test.ts, not just reasoned about: one deleting the only skill present, one deleting one of two skills so the newest remaining mtime is provably unchanged, the exact shape of the bug as found live. Both pass; both failed against the pre-fix code path when checked by reverting the fix locally before writing this entry.  Separately ruled out a false lead: a fresh dispatched subagent's own ambient "Available skills" listing also kept showing the pruned skill after the prune. Grepping this repo for the listing's header text turns up nothing, confirming that text is generated by the Claude Code CLI host itself, not by any Knight Code hook or a knightbrain_query call, so it is a separate caching mechanism outside this repo's code and this fix does not touch it. The two symptoms coinciding was circumstantial, not the same root cause.  The live MCP server process for this repo's own skills graph was already running when this fix landed, so its in-memory freshness logic is the pre-fix version until the server restarts; the stored graph.json here still carries the stale node until then. The fix is proven by the unit tests, which exercise the real code path directly rather than through the long-running server process.
