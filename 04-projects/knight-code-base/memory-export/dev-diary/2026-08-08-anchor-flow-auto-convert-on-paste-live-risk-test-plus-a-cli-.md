# Anchor Flow: auto-convert-on-paste live risk test, plus a CLI crash investigation

Ran the first live risk test for Anchor Flow's auto-convert-on-paste feature (never tested beyond unit tests before this session), plus confirmed the settings tab's default position/width reach the manual toolbar flow. Both requested by Chris before deciding on push for local commits 2b6d68d and 970d032.  Setup: the test vault's installed main.js predated both commits (built 08-07 18:54, commits landed 08-08 09:57), so rebuilt from source (tsc's TS2688 false negative confirmed harmless again, esbuild direct produced a valid main.js) and redeployed to Plugin Tester before testing anything.  Method: real paste and drop events dispatched via the obsidian CLI's eval command against the live app, not mocked. Constructed a real File from an existing test image's bytes, wrapped in a DataTransfer, dispatched as ClipboardEvent('paste')/DragEvent('drop') on the CodeMirror content DOM. This exercised Obsidian's own real default attachment-creation pipeline, not a stand-in.  Findings: - Paste and drop both PASS: real attachment created by Obsidian's own default handling, real vault.on('create') event, real 50ms-delayed conversion to the anchor-managed tag, confirmed correct in both Live Preview (getComputedStyle) and Reading mode (screenshot). - Settings-driven defaults reach both the auto-convert path and the manual toolbar path, confirmed separately for each. The manual toolbar check used a real synthetic click on a genuinely unconverted embed and read the toolbar's own DOM state (is-active class, width input value) rather than inferring from auto-convert alone. - Large image (15MB, real disk write) and an artificially slowed vault write (adapter.writeBinary patched with a 400ms delay) both still converted correctly, meaning the 50ms window is not threatened by size or by slow disk I/O specifically. - Rapid multi-paste is a real, reproducible FAIL: two images pasted back to back (no delay) land on the identical Obsidian-generated filename whenever they fall within the same wall-clock second (Obsidian's own attachment naming has one-second granularity, confirmed by inspecting the vault's real file list after each run, independent of whether the two images had identical or deliberately distinct byte content). Only one create event fires for that collided path, and the plugin's text.indexOf(expectedLink) search then matches only the first of the two now-identical embed occurrences, leaving the second a normal, working, unconverted embed. Not data loss, not a broken paste, but a genuine gap in the toggle's promise under back-to-back multi-image pasting. - One measurement artifact caught and NOT reported as a finding: an in-page setTimeout polling loop measuring the create-to-text-landing gap returned an implausible ~900ms reading that contradicted every functional result. Diagnosed as Electron/Chromium background-tab timer throttling distorting the poll, not a real timing gap, since the large-image and slow-write functional tests (which don't depend on fast in-page polling) both succeeded cleanly.  Separately, mid-session, Chris got a live "Uncaught Exception: SyntaxError ... is not valid JSON, at JSON.parse, at Socket.n" crash dialog in Obsidian. Root-caused rather than just retried: an earlier obsidian CLI append call had passed a long, prose-heavy, backtick-and-quote-dense content string through a bash DOUBLE-quoted argument. Bash interprets backticks inside a double-quoted string as command substitution, confirmed live with a minimal repro (a single backtick-wrapped span silently became an empty string, no bash error surfaced). At the scale of the original payload (many backtick spans across a long multi-paragraph string) this apparently produced a malformed argument that broke the CLI socket protocol's JSON framing. Confirmed the exact vulnerable code by extracting the live, version-matched obsidian-1.13.4.asar from %APPDATA%\obsidian\ (the static resources\app.asar in the install directory was a stale, differently-versioned copy with completely different line numbers, the same stale-asar trap already documented in this account's Lessons file for CSS work, now confirmed to apply to CLI investigation too): an unguarded JSON.parse(g) inside the CLI socket server's newline-delimited data handler, no try/catch around it. The app's renderer survived (eval/dev:errors kept responding, plugin settings and vault content were intact afterward), so this is not fatal, but it is a real way to pop a crash dialog on the user's screen. Confirmed the fix: the identical content sent via a single-quoted bash string (which suppresses all bash expansion) preserved the backticks verbatim and appended cleanly, no crash. Logged as a durable pitfall via learnings_log (skill obsidian-cli) rather than left to be rediscovered.
