# Repairing checks that passed without reading anything

Started as a question about how the knowledge base felt to operate in, and turned into repairing the layers that were quietly answering wrongly. The through-line: several checks were reporting success without having examined anything, which is worse than an absent check, because a silent pass reads exactly like a clean result.  The skills graph indexed only local skills, so fourteen invocable plugin entries and the winui:winui-dev agent were invisible. Chris pushed back on my framing when I wrote that limit down as documentation instead of fixing it, and he was right: the graph is the first-resort authority on whether something exists, so a lookup returning nothing is read as proof of absence, and a run could conclude a capability was missing and hand-build a replacement. Indexing the content turned out to be only half of it. The freshness check compared input mtimes and watched only local directories, and an mtime comparison cannot see a change to the indexer's own code, so every stored graph still looked current and was never rebuilt. Fixed with plugin content watching plus a revision stamp, since nothing else reaches a graph whose inputs did not change.  Twenty-one of sixty-six decision records were corrupted at rest, not rendered wrong as first reported. A malformed tool call collapses later parameters into an earlier field and leaves its separators as literal text, and the write path stored it unchecked. Repairing the snapshot alone would have been reverted, since it is recomputed from the event log, so the log itself had to be repaired, with word-for-word verification that nothing moved except into its correct field. The guard now rejects that shape at the shared gate covering all six stores. It then caught me three times in the same session, which is the strongest evidence available that it was needed. The fault is in how a call with several long parameters gets emitted, and putting the long parameter first is a reliable workaround.  Both halves of the quality gate compared only base...HEAD. Work here lands on the default branch, so that range is empty and both checks reported clean without reading a line. Untracked files were invisible even after that fix, since git diff cannot see a file git does not track. Proven with probes rather than reasoned about.  The test suite sat at nine failures, and they were hiding more than noise: a script spawned directly could not execute on Windows, so nine tests exercised nothing and two passed on that failure rather than on behavior. A permanently red suite also meant telling new breakage from expected breakage required re-running a baseline first.  Two false positives came from the token-optimizer plugin, both attributing a subagent's activity to the primary session. The read cache asserted a file was unchanged, contradicting the standing rule to read rather than reconstruct; fixed via its own env opt-outs rather than by editing the plugin cache, which gets replaced on update. The refetch guard has no such switch, so that one is documented rather than fixed.  Process note worth keeping: Chris told me to stop bringing each finding back as a decision and to fix things as they came up. The pattern was mine, not the work's. Every item I had queued as a question had an obvious right answer available from the code.
