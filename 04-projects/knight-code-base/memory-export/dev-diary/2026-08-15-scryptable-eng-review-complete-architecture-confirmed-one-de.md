# Scryptable Eng Review complete: architecture confirmed, one design assumption invalidated by real-world policy change

Ran formal-dev-workflow's Phase 3 (Eng Review) for feature protocol-whisper-app against the already-approved CEO and design review docs. Wrote protocol-whisper-app-eng-review.md, updated protocol-whisper-app.json to phase "security" with completedPhases ["ceo","design","eng"].  Confirmed with real technical detail: export libraries (python-docx, fpdf2, both pure Python, no external binary to bundle), Obsidian's direct markdown write mechanics, the five accessibility gaps' actual Qt/Win32 API implementations (QAccessible live regions, setAccessibleName, Qt tab-order chains, SystemParametersInfo for reduced motion), and diarization's credential/device/cache design (keyring for HF token storage, torch.cuda.is_available for device selection, HuggingFace's own cache dir).  The real finding: decision 085a69e9 (Scryptable's "Sign in with Anthropic" OAuth, using an existing Claude Pro/Max subscription's included usage) was logged in good faith at the time but is now factually wrong. WebSearch confirmed Anthropic banned exactly this: enforcement against Max OAuth in third-party clients began January 9 2026, a policy clarification followed February 19, and full enforcement against Pro/Max/Team subscription usage through any third-party OAuth-routing tool landed April 4 2026. Today is August 14 2026, four months into full enforcement. This is not a stale claim to hedge around, it is current and verified. Building the already-mocked OAuth toggle as designed would ship a feature that violates Anthropic's own Consumer Terms of Service.  This is exactly why eng review verifies technical claims instead of carrying design-review assumptions forward unchecked: a CEO/design review can approve a feature that sounds right at the time and still be wrong by the time engineering gets to it, if the outside world moved. Not fixed unilaterally: three real options were written up (API-key-only for Anthropic, a narrower check for any sanctioned alternative, or routing through a local Claude Code install) and handed to Chris rather than silently picking one, since dropping a capability he explicitly asked for is a real loss he should decide on, not something an eng review should quietly absorb.  Second real open item, lower stakes but still genuine: bundling a CUDA-enabled PyTorch build in a PyInstaller onefile exe runs 2.6 to 5GB (WebSearch-confirmed), against roughly 150-200MB CPU-only. One universal build isn't practical. Two options (separate GPU/CPU download variants, or one lightweight installer with a first-run accelerator download) both have real tradeoffs, handed to Chris rather than picked here.  Both open items logged as a single promise_log entry so they don't get silently dropped before Phase 3.5 Security Review, which has its own real stake in the OAuth item specifically (token handling is literally in its threat-model scope).
