# Scryptable Phase 3.5 Security Review complete: APPROVED_WITH_CONCERNS, 4 findings, no CRITICALs

Completed formal-dev-workflow's Phase 3.5 Security Review for protocol-whisper-app, run as knightcode-cso's deep-scan mode (2/10 confidence bar) against the planned architecture and spec (CEO/design/eng review docs, whisper_app_design.pen), since no Scryptable code exists yet to scan.  Built a real architecture mental model first: fully local desktop app, no Scryptable account system in v1 (removes a whole class of risk), 8 named trust boundaries including the two new ones this session added (MCP client connecting out, MCP server accepting connections in).  4 real findings, none CRITICAL: 1. HIGH (confidence 7/10): zip-slip path traversal in Craig archive import. Once Scryptable ships to real users (already the CEO review's stated bar), a booby-trapped zip claiming to be a recording is a realistic delivery vector. Needs a path-containment check before any extracted file gets written, standard fix, just needs to be a named task-breakdown requirement. 2. MEDIUM-HIGH (confidence 6/10): the new "Allow external agents to connect" MCP-server toggle needs to default OFF and require a locally-generated shared token, not just bind to localhost, since localhost alone doesn't stop other local processes from reaching it. Cited Jupyter's own local-token pattern as the precedent to follow. 3. MEDIUM (confidence 6/10): MCP client tool output is a real prompt-injection surface once a user connects a third-party MCP server, since tool results flow back into the LLM handoff chat as context. Recommended visually distinguishing first-party vs third-party tool calls in the transcript and a confirm step before third-party-triggered disk writes or outbound calls, extending the design's own existing "visible tool use over silent automation" pattern rather than inventing a new one. 4. LOW/informational (confidence 4/10): the local/custom endpoint field isn't a current SSRF risk since the user types it themselves in v1, but documented a standing rule against ever letting it be set silently from imported or remote content in a future version.  Confirmed sound with no finding: API key/HuggingFace token storage via keyring (Windows Credential Manager, appropriate for a single-user desktop app), payment-data handling (none exists in v1, the deferred paid REST API tier gets its own pass later), workspace/vault path validation (already named in the CEO review), corrections/vocabulary JSON handling (correctness issue already covered, not a security one). OAuth token handling turned out moot, already eliminated this session by dropping OAuth entirely.  Logged decision 043c2c8b with the full findings summary. Updated the vault's Scryptable/00 Overview.md and Projects/_index.md to reflect this, in the same pass, not left for later.
