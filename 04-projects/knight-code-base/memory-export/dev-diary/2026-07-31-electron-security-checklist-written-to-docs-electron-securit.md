# Electron security checklist written to docs/ELECTRON_SECURITY_CHECKLIST.md

Filled the gap DevKnight's own agent definition flagged: a dedicated Electron-specific security checklist covering contextIsolation/sandbox/nodeIntegration, preload/contextBridge surface, IPC validation, CSP/navigation, the deprecated remote module, and autoupdater signature verification. Written as a general Knight Code reference doc (parallel to docs/LESSONS_FROM_OBSIDIAN.md), not scoped to KnightOS, so any future Electron work routed through DevKnight can use it directly.  Researched via WebSearch against Electron's own current security docs and real disclosed issues rather than working from recall alone. Two concrete findings worth flagging for anyone reading this later: (1) electron-updater's Windows signature verification had a real disclosed bypass, CVE-2024-39698 / GHSA-9jxc-qjr9-vjxq, fixed in 6.3.0-alpha.6, relevant to KnightOS's electron-builder/electron-updater pick (decision 0c6d4004), the pinned version should be checked against that floor before any auto-update-enabled build ships. (2) <webview> tags do not inherit a parent BrowserWindow's webPreferences, a real independent-review point if KnightOS or any future app ever adds one.  Section 8 addresses KnightOS's own highest-privilege surface directly: a terminal-embedding app's threat model is not "contain the renderer from doing dangerous things" (that would defeat node-pty's purpose), it is "keep the IPC channel shape narrow, never grant more OS privilege than the user's own terminal already would, and treat the elevated-tab bridge as the one surface deserving independent hardened design." Explicitly tied to Milestone 1 Task 11's elevated-terminal research/design gate (decision f7bcc9be): the checklist's sections 2-4 (preload surface, IPC validation, navigation) should be run against that specific bridge design as part of the gate, not just against ordinary renderer-to-main IPC.  One honesty note, not written into the doc itself since it would read as history narration there: the dispatch prompt asked to tie the production-hardening section to "the debug-logging fix you just applied in the simplify pass." decision_search, dev_diary_search, and learnings_search turned up nothing matching that description, only an unrelated electron-log double-logging fix (duplicate unhandledRejection catching). Wrote section 7 as a general principle instead of citing an unverified specific incident, per the standing verify-don't-guess rule. If a real fix exists somewhere under a different description, it should get its own decision_log or dev_diary_log entry so this checklist can cite something real.
