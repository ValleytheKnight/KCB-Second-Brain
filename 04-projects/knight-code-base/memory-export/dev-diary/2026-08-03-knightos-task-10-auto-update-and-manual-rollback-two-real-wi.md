# KnightOS Task 10: auto-update and manual rollback, two real Windows/Electron bugs found and fixed

Built Task 10 of KnightOS's Milestone 1 in an isolated worktree (C:\Users\Chris Brown\Documents\DevPrograms\KnightOS-task10, branch task-10-auto-update off master at 8fc7749), run in parallel with Project Tabs Task C in the main working directory, deliberately never touched. electron-updater (generic provider, see the matching decision entry for the hosting tradeoff) checks automatically on every packaged launch, auto-downloads once an update is found, and surfaces a banner ("Restart and Install") once ready, driven entirely by real IPC (UpdateCheck/UpdateInstall/UpdateStatusChanged/RollbackStatus/Rollback) rather than Electron's own default update dialogs. A background auto-check failing (no real update host configured yet) stays silent; only a manually triggered check (the new Help menu items) surfaces an error banner, so an unconfigured feed doesn't nag on every launch.  Manual rollback (electron-updater has no built-in concept of this) is a real single-snapshot design: before installDownloadedUpdate() hands control to the downloaded installer, backupCurrentInstall() copies the entire currently-installed directory into a staging path next to it and only swaps it into place via an atomic rename, so a crash or disk-full mid-copy never corrupts a previously-good snapshot. Rollback itself needed a detached PowerShell helper, since a running app holds its own exe and native addons (node-pty's conpty.node) open on Windows, so the actual directory swap cannot happen from inside the process being replaced; the helper waits for the app's real PID to exit, copies the backup into staging, validates the real exe is present before touching anything live, swaps via rename with the pre-rollback install kept aside until the swap is confirmed, then relaunches.  Two real bugs surfaced only by live verification, not by typecheck or unit tests, both durable lessons for any future Electron/Windows work in this codebase:  1. electron-updater ships as CommonJS. `import { autoUpdater } from 'electron-updater'` compiled and typechecked cleanly but crashed the real running app at launch with "Named export 'autoUpdater' not found," since Node's ESM loader determines a CJS module's named exports via static analysis (cjs-module-lexer) rather than actually running the module, and that analysis doesn't reliably resolve this particular package's export. Fixed with the standard interop pattern: `import electronUpdater from 'electron-updater'; const { autoUpdater } = electronUpdater`. Caught by launching the real built app directly (not through Playwright) after a coordinator flagged the crash live.  2. A Node child_process.spawn call with `detached: true` plus `.unref()` is the documented way to outlive a parent process, but confirmed live that this is not sufficient for a process spawned from inside an Electron app on Windows specifically: Electron's own processes are grouped under a Windows Job Object that tears down its child processes when the browser process exits, and a plainly detached child does not automatically escape that job. The rollback helper vanished with zero trace (no log entry, no file-swap effect) the instant the app quit, both with a graceful app.quit() (which itself also sometimes failed to actually terminate the process at all, a separate real symptom) and with a forceful app.exit(0). Fixed by routing the spawn through `cmd /c start`, which performs its own independent CreateProcess call and reliably escapes the parent's job object, a documented real-world workaround for this exact class of problem. Root-caused by direct evidence, not guessed: confirmed the main process was still alive minutes after quit via a live process query, then confirmed the fix by tampering a real disposable packaged install's files, triggering the full real backup-then-rollback cycle end to end, and confirming the tamper was genuinely reversed and the relaunched app started cleanly, twice, once before and once after the fix, isolating exactly which change closed the gap.  electron-updater confirmed at 6.8.9 in the real installed node_modules, above the 6.3.0-alpha.6 floor tied to CVE-2024-39698 (checked directly, not assumed from the package.json range).  Code-signing's absence (deliberately deferred, decision ae12c6ac) does not block the auto-update feature from working, verified end to end without a cert. It does weaken what electron-updater's integrity check actually proves: without a real Authenticode signature, there is nothing for the post-CVE-2024-39698 signature verification to check, so integrity for a downloaded update reduces to HTTPS transport plus a SHA512 hash comparison against latest.yml, which protects against a corrupted download but not against a compromised or spoofed hosting server able to serve a tampered file alongside a matching hash for it. Real, bounded risk for personal single-user software where Chris controls the hosting server, but a materially weaker guarantee than a signed build would have, worth closing once code signing lands.
