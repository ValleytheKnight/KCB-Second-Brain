# browse daemon fully repaired: playwright, sharp, and their real dependencies were missing entirely

Resolves the two browse-skill regressions logged earlier this session (the sharp/detect-libc mismatch, and the daemon failing to restart at all). Root cause, found by actually running the server directly instead of guessing further: `node C:\Users\Chris Brown\.claude\skills\knight-code\browse\dist\server-node.mjs` threw `ERR_MODULE_NOT_FOUND: Cannot find package 'playwright'`. The earlier bare `npm install <single-package> --no-save` calls in that directory (which has no `package.json`, only a near-empty `package-lock.json`) had each pruned other packages as "extraneous" relative to that one command, ultimately removing `playwright`, `playwright-core`, `diff`, `@ngrok/ngrok`, `socks`, `zod`, and `marked` entirely, not just leaving a version mismatch.  Found the real, authoritative dependency list by reading Knight Code's own tracked source for this tool: `browse/scripts/build-node-server.sh` names the exact packages the compiled Node bundle externalizes at build time (`playwright`, `playwright-core`, `diff`, `bun:sqlite` [stubbed on Windows], `@ngrok/ngrok`, `sharp`), and the repo root `package.json` has the real pinned versions (`playwright ^1.58.2`, `sharp ^0.35.3`, `@ngrok/ngrok ^1.7.0`, `diff ^7.0.0`, `socks ^2.8.8`, `zod ^4.4.3`, `marked ^18.0.2`). Reinstalled all of them together in one `npm install` call (not one-at-a-time, to avoid npm treating any of them as extraneous relative to the others again), which restored `playwright`/`playwright-core`/`diff`/`marked`/`socks`/`zod` alongside the already-present `sharp`/`detect-libc`/`@ngrok`.  Verified end to end, not just that the daemon starts: `browse status` reports healthy, `browse goto https://example.com` navigates successfully (200), and `browse screenshot` (the command that started this whole investigation) produces a real, valid PNG file. This closes both earlier regressions; no further action needed on them.  Lesson for next time, worth repeating since it bit twice in one session: never run a bare `npm install <single-package> --no-save` inside a `node_modules` directory that has no real `package.json`, npm has nothing to constrain the install against and will prune anything not part of that one command's tree.
