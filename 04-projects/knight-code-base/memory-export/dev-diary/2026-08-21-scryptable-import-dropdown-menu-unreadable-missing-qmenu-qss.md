# Scryptable: Import dropdown menu unreadable, missing QMenu QSS rule, fixed and pushed

Chris sent a screenshot: the Import dropdown (its three options, "Discord Bot Archive (Craig)...", "Multi-Track Audio Files...", "Single Recording...") rendered with dark, near-illegible text on a dark popup background.  Root cause: `src/scryptable/theme.py`'s `stylesheet()` never declared a `QMenu` rule at all, unlike every other themed widget in the app shell. The generic `QWidget { color: ... }` rule still supplied a text color via cascade, but nothing supplied a background, so the popup's actual background fell through to Qt's/Windows' native popup chrome instead of the app's own palette. With Windows in dark mode and the app running its Light theme (`text_primary` = `#2A2520`, near-black), the result was near-black text on a near-black native popup background. Same failure class as the `WA_TranslucentBackground` window-paint bug fixed earlier in commit `6ea4761`: partial QSS coverage leaves a gap the OS fills in unpredictably, rather than the app fully owning its own paint.  Fix: added explicit `QMenu`/`QMenu::item`/`QMenu::item:selected`/`QMenu::item:disabled`/`QMenu::separator` rules to `theme.stylesheet()`, using the same palette tokens (`surface`, `text_primary`, `border`, `primary`, `on_primary`) every other themed widget already uses. This fixes every `QMenu` popup in the app, not just the one screenshotted (the standalone Import popup `MainWindow.request_import()` builds, plus every `QMenuBar` submenu `chrome.build_menu_bar()` builds: File, Edit, View and its nested Theme submenu, the Recording-named unit menu, Help).  Verified with real evidence: rendered the actual Import menu widget with real Windows GDI rendering (not the pytest-qt offscreen platform) for both Light and Dark themes, inspected the screenshots directly (text reads clearly against its background in both), and separately sampled real rendered pixel colors at the menu's background corner, confirming an exact match to the palette's `surface` hex (`#FFFFFF` light, `#28241F` dark) rather than an OS-supplied color.  Added a new regression test file `tests/test_theme.py`: both palettes' `QMenu`/`QMenu::item`/`QMenu::item:selected` rules exist and reference the intended palette tokens, and the default (unselected) item's surface/text-color pair is asserted to meet WCAG AA contrast (>=4.5:1) via a hand-computed relative-luminance check, matching the same manual-WCAG-verification approach already used for the app's badge/banner colors (decision `d8815d8b`). Deliberately did not hold the selected/hover state (`primary`/`on_primary`, ~2.46:1) to the same bar: it reuses the existing primary-orange-background/white-text pattern already used on every primary button across the app, a separate, pre-existing design choice out of scope for this fix, not something newly introduced here.  Not caught by the existing pytest-qt suite before this fix, and would not have been: no test exercised `request_import()`'s menu visually, only its logic. 145/145 tests pass after the fix (144 pre-existing plus the new theme test file's 2 tests).  Ran `/simplify` (reviewed directly given the small ~86-line diff rather than spawning four parallel agents; no existing contrast/luminance helper found to reuse, no simplification/efficiency/altitude issues found) and `/code-review` per this repo's standing post-commit hook.  Committed and pushed as `0fac271` to `https://github.com/ValleytheKnight/Scryptable` (master).
