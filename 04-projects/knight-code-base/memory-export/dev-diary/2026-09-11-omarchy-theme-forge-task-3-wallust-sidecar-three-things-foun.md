# omarchy-theme-forge Task 3: wallust sidecar, three things found by checking rather than assuming

Built the digest-verified wallust sidecar for omarchy-theme-forge (commit f74361d, local only). Three findings worth keeping, each of which would have produced wrong work if taken on assumption.  The reference implementation the task breakdown named does not exist at the path it names. Task 3 says to reuse omarchy-powerplan's scripts/install-privileged-helper and .github/workflows/verify-helper-digest.yml. That repo has no scripts/ directory, and the workflow is named verify-privileged-helper.yml. The installer was real and was then removed by commit 34dada1, which replaced the in-checkout installer with an AUR PKGBUILD carrying the pin in sha256sums. `git show 25ce61f:scripts/install-privileged-helper` still returns the full original, which is where the error style (progname: message to stderr, exit 1) and the pinned-constant comment convention came from. Logged separately as a learning.  The wallust release asset is a tarball, not a bare binary. Codeberg ships wallust-<version>-<triple>.tar.gz in plain and -with-assets variants; the plain one holds exactly one member named wallust. That is why two digests are pinned instead of one. Also noted for future version bumps: release 3.4.0 ships assets still named 3.3.0, so the asset filename cannot be derived from the tag by pattern alone.  bundle.externalBin is load-bearing even with bundle.active false. That looked like a fair objection worth testing rather than asserting. Removing the sidecar and rebuilding fails at tauri-build with "resource path `binaries/wallust-x86_64-unknown-linux-gnu` doesn't exist". The same build output prints TAURI_ENV_TARGET_TRIPLE=x86_64-unknown-linux-gnu, confirming the gnu naming the task assumed; the musl build is static-pie per file(1), so it runs unchanged under that name.  One design note on verification. Proving "a corrupted binary aborts the build" by editing the pinned constant would test the wrong thing: it shows the comparison runs, not that a bad download is caught before placement. The fetch script takes WALLUST_SIDECAR_ARCHIVE, a local copy of the release tarball, which skips the download and keeps both digest checks. Flipping one byte with dd and pointing the variable at it produced the real failure: both digests printed, exit 1, src-tauri/binaries/ left holding only .gitkeep. The variable stays in because it also covers an offline build, not as test-only scaffolding.
