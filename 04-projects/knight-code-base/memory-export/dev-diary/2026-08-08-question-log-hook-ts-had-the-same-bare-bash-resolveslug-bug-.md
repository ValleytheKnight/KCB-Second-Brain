# question-log-hook.ts had the same bare-bash resolveSlug bug, silently degraded since introduction

Commit 274ecbb fixed bash resolution in bin/knight-slug's callers (session-start-memory-hook.ts, mnemosyne-proxy/server.ts) by migrating them to the shared resolveKnightSlug() in lib/knight-slug.ts, which resolves bash by absolute path instead of assuming a bare "bash" resolves via PATH. hosts/claude/hooks/question-log-hook.ts (added in c2bdff0, 2026-07-27) had its own independent resolveSlug() that still called execFileSync('bash', ...) directly and was missed by that fix.  Root cause and impact: bash only resolves on PATH inside an interactive Git Bash session (it injects its own bin dirs at shell startup). PreToolUse/PostToolUse hooks are spawned directly by Claude Code, not through Git Bash, so resolveSlug threw on every real invocation, slug came back null, and the hook's own `if (!slug) process.exit(0)` silently no-op'd the entire hook. Confirmed live with a smoke-test invocation before the fix would have failed the same way session-start-memory-hook did pre-274ecbb.  Concretely this meant, for the ~12 days the question-log/preference system existed before this fix: two-way standing preferences never actually auto-answered a question (PreToolUse interception never fired, so every eligible question kept reaching Chris), and no question was ever logged as `asked` via PostToolUse. Both failures were silent, visible only in ~/.knightcode/hook-errors.log.  Fix: replaced the hook's local resolveSlug() with the shared resolveKnightSlug() from lib/knight-slug.ts, same pattern as the other two call sites. Verified with a live smoke-test invocation outside a Git Bash session, which resolved the slug and logged correctly (test entry then removed from the real question log and invocation log).  Lesson: when a shared resolver gets extracted specifically to fix a class of bug, grep for all prior independent implementations of that same logic before considering the fix complete, one was missed here because the fix commit only touched the two call sites it happened to be actively working on.
