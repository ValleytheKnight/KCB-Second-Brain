# Scryptable: code review caught two more contrast defects in the QMenu fix, fixed and pushed

Follow-up to the same-session Import-dropdown-menu contrast fix (commit `0fac271`). Ran this repo's standing post-commit `/code-review` pass against it, per Chris's standing rule that code work isn't done until both `/simplify` and `/code-review` have run.  Review found the commit correctly fixed the reported bug (unreadable default-state menu text) but introduced two new contrast defects of the exact same class, neither covered by the regression test as first written:  1. `QMenu::item:selected` used `primary`/`on_primary` (`#FF8400`/`#FFFFFF`), 2.46:1 contrast, under WCAG AA's 4.5:1 for normal text. This reuses the app's existing primary-button color pair, but a menu item's hover/keyboard-highlight text is normal-size body text hit on every routine hover or arrow-key navigation, not a bold button label, so it's a real, frequently-triggered readability defect, not an edge case. 2. `QMenu::item:disabled` and `QMenu::item:selected` have equal QSS specificity, so an item that is simultaneously disabled and the active/hovered one kept the `:selected` background with an ambiguously-resolved text color, measuring 1.05:1 in Dark. Latent (no `QAction` in the codebase called `setEnabled(False)` yet at the time) but live the instant one does.  Fix: switched `QMenu::item:selected` to the `border`/`text_primary` pair `QMenuBar::item:selected` already uses in the same file for the top-level menu-bar hover state (10.3-10.9:1 in both palettes), rather than inventing a new, weaker pattern. Added an explicit `QMenu::item:disabled:selected` compound-selector rule (`background: transparent`, `text_secondary`) to resolve the ambiguous cascade deterministically: a two-pseudo-class selector has higher CSS2 specificity than either single-pseudo-class selector, so it wins regardless of declaration order.  Verified with the same rigor as the original fix: extended `tests/test_theme.py` to assert WCAG AA contrast for all four real item states (unselected, selected, disabled, disabled+selected). For the selected state specifically, a first attempt at a real pixel check used a synthetic `QTest.mouseMove`, which produced no visible highlight since `QMenu` only tracks hover/active state through its own internal event handling during a real `exec()` loop, not from a bare mouse-move sent to an unshown popup; switched to the real public `QMenu.setActiveAction()` API, which reliably forces the same visual state a real hover produces, then grabbed a real on-screen render and sampled the highlighted item's background pixel directly: exact matches to `palette.border` in both themes, confirmed visually in the saved screenshots too.  Committed and pushed as `ef9cade` to `https://github.com/ValleytheKnight/Scryptable` (master). 145/145 tests pass (existing test functions extended, not new ones added). Updated the DevKnight Workshop vault: a new follow-up subsection under the Import-dropdown follow-on section in `Projects/Scryptable/06 Lessons Learned/Task 7 Diarization Integration Build Notes.md` (also corrected that section's earlier claim that the selected-state contrast was an intentionally out-of-scope pre-existing pattern, since the code review showed it was a real, in-scope defect), `00 Overview.md` Continuation Point, and `Projects/_index.md`'s Scryptable one-liner.
