# Built the knight-watch system watchers, and why the rkhunter one was invisible

Chris asked to make sure the crash-diagnosis session and a malicious-activity session both start with permission checks bypassed, and to add AIDE and ClamAV watchers alongside the rkhunter one.  What was already there, and the reason a first search missed it: an rkhunter notify chain existed (`rkhunter-notify.path` watching `/var/log/rkhunter-last-exit`, feeding `omarchy-agent-rkhunter`), but it was split across `/usr/local/bin`, `/etc/systemd/system`, `~/.local/bin` and `~/.config/systemd/user`, with no single file naming all four pieces. A grep for "malicious" in the repo found nothing, a grep for the tool names in `/usr/bin` found nothing, and the decision log recorded only the AIDE and ClamAV installs, not any notification wiring. Every individual check was correct and the conclusion was still wrong. `docs/SYSTEM_WATCHERS.md` plus the CLAUDE.md pointer exist so that failure mode cannot repeat.  Two facts that shaped the design, both measured rather than assumed:  Quickshell executes notification clicks itself, from the `omarchy-exec-argv` hint, using its own PATH. That PATH puts `/usr/share/omarchy/bin` first, ahead of `~/.local/bin`. Shadowing a packaged `omarchy-*` script from the user bin directory therefore cannot work for a notification click, which killed the cheapest option for changing the permission flag. Every `--exec` in the new scripts uses an absolute path for the same reason.  The rkhunter chain had never actually fired. `rkhunter-scan.service` was still `inactive (dead)` with the timer set to `OnCalendar=weekly`, and neither `/var/log/rkhunter-last-exit` nor the summary file existed. The wiring looked correct and was completely unproven, which is what `knight-watch test <​tool>` now exists to settle: it sends a real notification through the real bus, and clicking it opens a session that reports back which permission flag it was launched with.  One gap found while designing rather than after: a systemd `.path` unit only watches while the user session is up, so a scan finishing while logged out would go unannounced and never be replayed. `knight-watch-catchup.service` re-runs every check at login, and `knight-watch-check` fingerprints each announced result under `~/.local/state/knight-watch/` so the catchup pass and the path unit cannot both toast the same finding.  AIDE needed a producer built from nothing. The packaged `aidecheck.service` runs `aide --check` straight into the journal and writes no result file, so there was nothing for a path unit to watch. A drop-in points its ExecStart at `/usr/local/bin/knight-scan-aide`, which is a drop-in rather than an edit because the unit belongs to the aide package.  ClamAV's original scan script appended to a shared log, so grepping it for FOUND lines would have resurfaced findings from earlier weeks as if they were new. The wrapper scans into a fresh temp log, quotes only that run in the summary, and appends to the shared log afterward.  The root half needs a password and this machine has no polkit authentication agent running (only polkitd itself), so `pkexec` is not available either. That half is handed to Chris as a single `sudo ./install-root.sh`.
