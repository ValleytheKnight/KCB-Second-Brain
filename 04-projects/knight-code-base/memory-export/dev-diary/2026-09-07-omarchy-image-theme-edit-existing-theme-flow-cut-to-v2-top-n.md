# omarchy-image-theme: edit-existing-theme flow cut to v2, Top Nav v2-labeled, Missing Dependency screen reframed for bundled wallust

Chris cut the entire edit-existing-theme flow from v1 to v2 during Phase 2 design review (decision b0439759, reversing the CEO-review acceptance of item #7 in decision b0f0cda9). Logged the decision and updated the CEO plan doc (ceo-plans/2026-09-06-omarchy-image-theme.md) at its source: row 7 of the Scope Decisions table now reads "ACCEPTED, then CUT TO V2", the General theme editor bullet moved out of Accepted Scope into a new Deferred to v2 section, and the Dream State diagram's THIS PLAN column no longer claims "edits any existing theme too".  On the live Pencil canvas (Pen Designs/omarchy-image-app.pen), applied a consistent v2 treatment to the Edit Existing Theme tab on all 10 Top Nav instances that carry Mode Tabs (the 11th, on the Startup - Missing Dependency screen, has Brand only by earlier design and was correctly left untouched): forced the tab's fill to transparent and opacity to 0.55 regardless of that screen's previous active/inactive state, set the tab label to $text-secondary, and added a small V2 pill badge (fill $surface-2, stroke $border, "V2" text in $font-heading) as a sibling of the label inside the tab frame. This replaces the prior per-screen inconsistency where the Edit tab rendered as accent-colored/active on the three edit-flow screens themselves (Selection, Loaded, Error) despite those screens now being fully out of v1.  Audited the full canvas by text-content search (/edit/i, /existing|open theme|load theme/i) rather than sampling: confirmed the Top Nav tab is the only navigation entry point into the edit-existing flow anywhere in the document. The "Edit Existing Theme button on the Save Conflict screen (ps2HX)" named in the assignment is that screen's own Top Nav tab (onhu6/SMmMm), not a separate body element; ps2HX has no other edit-flow entry point. The one other "Existing" match found, "Overwrite Existing" on ps2HX's collision-guard modal, is unrelated (it means an existing theme name colliding during a Generate-flow save, not opening an existing theme to edit), left as-is.  Frame RuK3j (Startup - Missing Dependency State) was reframed rather than deleted, given decision 9e7e95c7 (wallust is now bundled inside the app, not an AUR dependency the user installs). Judged a dedicated screen still earns its place: the CEO plan's own Foundational Decisions (line 53) require the app to detect at startup whether wallust and omarchy actually work and show a clear message if not, and a corrupted or incomplete app bundle is a real, if now rare, failure mode distinct from "please install wallust via yay". Reworded: heading to "Startup check failed", the intro detail text to explain wallust ships bundled while omarchy is the user's own system install, the wallust check-row label to "wallust (bundled), not found or unreadable", and the help text to point at reinstalling/repairing the app rather than `yay -S wallust`. The omarchy check row and its "found at /usr/bin/omarchy" success state were left unchanged, that half of the screen's premise is unaffected by the bundling decision.  Held per Chris's instruction after this work: no eng review, no further canvas changes, pending his review and a follow-up sweep once Agent B's 2 new screens (live-preview-thumbnail display, color-editing-interaction screens) land.
