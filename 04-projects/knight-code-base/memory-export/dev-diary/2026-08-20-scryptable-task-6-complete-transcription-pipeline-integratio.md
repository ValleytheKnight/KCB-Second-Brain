# Scryptable Task 6 complete: transcription pipeline integration, a real crash found and fixed mid-build

Proceeded to Task 6 (transcription pipeline integration) per Chris's own explicit go-ahead relayed by the coordinator, same standing process as Tasks 1-5.  Task 6's own description says "import transcribe_stems.py as a library," but the real script (found via filesystem search at C:\Users\Chris Brown\Documents\D&D\Felled God\Discord Episode Recording\transcribe_stems.py, outside this repo entirely, in Chris's own unrelated D&D campaign folder) is not a real importable library: its module-level code reads a hardcoded session-label-history.json and vocabulary-master.txt from that one personal workspace at import time, derives its target folder from that same hardcoded path, and calls sys.exit(1) on failure. Literally importing it would read Chris's live D&D session state as a side effect of starting Scryptable and could exit the whole process from inside a background thread. Ported the real transcription logic instead: transcription.py carries every tuned parameter value forward unchanged (language "en", VAD "silero", condition_on_previous_text False, refine_whisper_precision 0.2, model large-v3-turbo), verified byte-for-byte against the original script's own call by a spec-axis review, but takes a real recording folder as a parameter and raises a named TranscriptionError instead of exiting.  Built transcription_worker.py (background QThread), transcription_in_progress.py and recording_tab.py (the screens), plus the minimum real plumbing needed to trigger any of it at all: activating a Recording in the sidebar (no click handler existed anywhere before this task) opens a real per-recording tab, wired to Start Transcription in the Recording menu and a live progress label in the toolbar/ribbon, and Cancel Running Job (previously dead) now actually requests interruption, checked between stems since whisper_timestamped's synchronous API exposes no finer-grained cancellation point.  A real, serious bug was found and fixed during the build itself, not just in review: importing torch/whisper_timestamped for the first time on the background QThread, while the main thread's own Qt event loop kept running concurrently, crashed the whole process with a genuine Windows access violation. Reproduced directly with a real pytest run; confirmed the concurrency was the trigger by also running a minimal isolated repro (same import, no active event loop) which did not crash. This would have hit any real user's very first transcription click in a session. Fixed with transcription.warm_up(), called synchronously on the main thread before the worker thread ever starts; every import after the first, including the one the worker thread itself makes through _load_model, is a cached no-op.  Ran this project's standing hygiene pass before commit: banned-language scan (clean), then two parallel code-review sub-agents (Standards axis, Spec axis). Standards axis found two real hard violations (HISTORY-narrative content in transcription.py's own module docstring and in warm_up()'s docstring, both citing this task's own build process rather than stating pure mechanism), fixed immediately, plus one judgement-call smell applied (collapsed three near-identical transcription-lifecycle teardown methods into one shared _reset_active_transcription helper). Spec axis confirmed the ported parameter values match the real original script exactly, confirmed the new Recording-tab/sidebar-activation plumbing is reasonable necessary scope rather than creep, and caught two real implementation gaps: the ribbon-bar label hardcoded the word "Transcribing" for every progress event regardless of real status (fixed by extracting a shared transcription.format_progress() both the ribbon and the Transcription In Progress screen now call), and the background worker was constructed with no parent and no connection from Qt's own finished signal to deleteLater(), a real "QThread destroyed while thread is still running" timing risk since the custom finished_ok/failed/cancelled signals fire from inside run() just before it returns, not at the same moment the OS thread is actually confirmed done (fixed by parenting the worker to MainWindow and wiring finished to deleteLater). Added a regression test for the ribbon-label fix specifically.  Verification went beyond mocked tests: 110/110 pytest-qt tests pass, plus a real, non-mocked end-to-end run using the actual cached large-v3-turbo model on this machine's own CUDA GPU (a short synthetic WAV clip, completed in under 30 seconds, produced a real, valid .words.json), and a real corrupt-audio file run confirming a named TranscriptionError surfaces rather than a raw exception. Re-ran the real end-to-end smoke test again after the review-driven fixes to confirm the worker-lifecycle change didn't introduce any new crash or warning, clean.
